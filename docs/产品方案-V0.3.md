# 今天干嘛｜产品方案 PRD V0.3

> **产品定位**：面向两个人的 AI 生活决策助手。平时随手收藏菜谱、餐厅、菜品、活动和待办；遇到「吃什么、玩什么」的选择困难时，基于共同灵感库快速形成可执行建议。  
> **交付载体**：响应式 Web Demo 为交互基线，正式版本优先适配手机端/微信小程序。  
> **文档状态**：V0.3 开发基线 · 2026-10-08  
> **参考原型**：`today-what-demo.html`。原型中的推荐与持久化为演示逻辑，不能等同于生产能力。

## 1. 背景与目标

### 1.1 用户问题

- 周末、下班后不知道去哪玩、做什么，反复沟通仍然难以决定。
- 经常不知道吃什么：自己做时不会搭配菜，出去吃时想不起曾收藏的餐厅和菜品。
- 灵感散落在截图、社交平台链接、相册、聊天记录中，收藏了但很少重新使用。
- 通用 AI 不知道两个人收藏过什么，也不了解长期偏好和实际做过的事。

### 1.2 产品目标

1. **随手存**：最少操作把图片、文字或链接变成可检索的结构化灵感。
2. **快速选**：以共同收藏为主，结合临时条件给出 1 个主方案、最多 2 个备选。
3. **能落地**：输出不仅有推荐名称，还应有菜单搭配或活动顺序、理由及必要的执行信息。
4. **有反馈**：能采纳、收藏待用、标记完成，并记录简单评价；下一轮推荐可以参考这些反馈。

**不追求**：完整生活日程管理、在线订餐、实时地图导航、自动订票、复杂多 Agent、自建推荐算法平台。

### 1.3 目标用户与原则

- 初始用户：固定的两个人，共享一个生活空间。
- 任意一人可以新增或修改收藏、发起 AI 推荐、采纳方案，无需双方投票确认。
- 首页优先强调 **做决定**，灵感库是输入手段，历史记录是反馈手段。
- 录入需轻量；信息不确定时可以留空或让用户补充，不能让模型编造事实。

## 2. MVP 范围与优先级

| 模块 | P0：V1 必做 | P1：后续考虑 | V1 明确不做 |
| --- | --- | --- | --- |
| 首页 | 「吃什么」「玩什么」双入口、灵感预览、快捷收藏 | 个性化快捷建议 | 信息流、社交广场 |
| 灵感库 | 分类查看、搜索/筛选、新增、编辑、删除 | 批量导入、重复识别 | 内容社交发布 |
| 收藏录入 | 文字、相册/拍照截图、粘贴链接、AI 提取草稿、人工确认 | 语音、外链自动解析 | 绕过平台权限抓取 |
| 吃什么 | 自己做 / 出去吃 / 帮我选；条件输入；结构化推荐 | 更完整的采购清单、食材库存 | 下单支付、餐厅实时搜索 |
| 玩什么 | 根据时间、预算、偏好、收藏活动组合方案；待办可选参与 | 天气、实时开放信息、路径规划 | 自动订票/预约 |
| 推荐操作 | 换一组、采纳并保存、保存待用 | 局部替换某个活动/菜品 | 多人审批工作流 |
| 我们的记录 | 待做/已完成；完成反馈：喜欢/一般/不喜欢 | 复盘统计与回忆相册 | 完整日历与提醒系统 |
| 双人空间 | 双人共享、简单成员标识、个人口味偏好 | 更复杂的权限和邀请管理 | 群组/组织架构 |

**开发原则**：P0 中的「两个决策场景」都要跑通，但每个模块先控制成最小闭环，不靠添加页面数量体现完成度。

## 3. 信息架构与页面清单

```text
今天干嘛
├── 首页（Home）
│   ├── 吃什么 → AI 决策页（mode: food）
│   ├── 玩什么 → AI 决策页（mode: play）
│   ├── 我们的灵感（最近收藏）
│   └── + 随手收藏
├── 灵感库（Ideas）
│   ├── 全部 / 菜谱 / 菜品 / 餐厅 / 活动 / 待办
│   ├── 搜索、筛选、详情、编辑、删除
│   └── 新增灵感（Add）
├── 我们的记录（Records）
│   ├── 待执行 / 已完成
│   └── 方案详情、标记完成、反馈
└── 双人空间设置（非主导航）
    ├── 成员、共享空间
    └── 个人偏好
```

### 3.1 首页

**目的**：一眼找到今日决策入口，不让用户先做内容管理。

- 主标题：「今天，我们干嘛？」
- 主场景卡片：`🍲 吃什么`、`🎡 玩什么`。
- 最近灵感：展示少量双方共同收藏，点击进入灵感库。
- 全局 `+ 随手收藏`：进入新增灵感页面。
- 主导航：`首页 / 灵感库 / 我们的记录`。

### 3.2 AI 决策页

**一套页面承载两个场景**，按 `food` / `play` 切换输入项和结果卡片。

- 公共输入：自然语言需求、预算、可用时间。
- 「吃什么」补充：`自己做 / 出去吃 / 帮我选`、口味、人数（默认 2）、是否优先已有收藏。
- 「玩什么」补充：`出门 / 宅家 / 都可以`、时段、偏好、是否包含待办。
- 主按钮：「帮我们决定」。
- 结果：主推荐 + 可选备选；来源标识 `我们的收藏` / `AI 新建议`；理由与可执行信息。
- 操作：`换一组` / `采纳并保存` / `保存以后再做`。

### 3.3 灵感库

- 卡片字段：图片（可选）、标题、分类、标签、添加人、来源、简短备注。
- 分类：菜谱、餐厅、菜品、活动、待办。
- 基础操作：按分类筛选、搜索标题/标签、查看、编辑、删除。
- 新增页：标题、描述、类型（AI 建议后可修改）、图片、链接、标签、必要的可选字段。
- 允许用户跳过 AI 识别，直接手动保存，避免模型不可用时阻塞录入。

### 3.4 我们的记录

- 只保存主动采纳或标记「以后再做」的方案；不自动保存所有生成结果。
- 状态：`saved`（以后再做）、`planned`（已决定）、`completed`（已完成）、`cancelled`（不做了）。
- 方案卡片展示：标题、场景、内容摘要、来源、创建时间、操作人、状态。
- 完成反馈：喜欢/一般/不喜欢，可选补充一句话。
- **V1 不做**：拖拽时间线、重复日程、复杂共享日历。

## 4. 核心用户流程

### 4.1 流程 A：收集生活灵感

1. 任意页面点击「+ 收藏」。
2. 选择：拍照/上传图片、输入文字、粘贴链接（允许混用）。
3. 点击「AI 帮我整理」后，模型尝试识别类别、标题、标签和其他可见信息。
4. 前端展示**可编辑草稿**，标注无法确定的字段。
5. 用户确认保存，内容进入两个人共同的灵感库。
6. AI 识别失败时，保留输入内容并支持手工保存。

**特别规则**：外链 V1 只保证保存原链接和用户补充内容，不保证可抓取小红书、抖音等平台的正文或图片。图片识别不能凭空补出门店地址、价格或菜谱完整步骤。

### 4.2 流程 B：吃什么

1. 进入「吃什么」，选择 `自己做 / 出去吃 / 帮我选`。
2. 描述条件，例如「今天想吃辣、两个人、40 分钟内、预算 100 元」。
3. 后端筛选收藏中的相关菜谱、菜品、餐厅及双方偏好。
4. AI 生成结构化结果：
   - **自己做**：2～3 道菜的组合，简要食材、耗时、推荐理由；时间为估计时需标注。
   - **出去吃**：2～3 个收藏餐厅/菜品组合，或明确标注的探索建议；未验证的营业时间、位置、价格不能写成确定事实。
   - **帮我选**：比较在家做与出去吃，推荐一种主方案，并给出简短取舍理由。
5. 用户换一组、采纳，或保存以后再做。
6. 执行后记录反馈。

### 4.3 流程 C：玩什么

1. 进入「玩什么」，描述条件，例如「周六下午 4 小时、不要太累、预算 200」。
2. 筛选已收藏的活动/地点，按需纳入未完成待办。
3. AI 输出半天或一天的活动组合；可包含时间顺序，但不提供未经验证的实时交通、活动开放状态。
4. 待办作为**可选项**，不应默认把约会变成家务排期。
5. 用户采纳、保存、完成并反馈。

### 4.4 流程 D：双人共享

- 两人属于同一 `space`，共享灵感、推荐记录与计划。
- 个人偏好可以不同；相互冲突时推荐折中方案或备选方案。
- 任意一人可以单独采纳、修改记录；系统保留操作人信息。
- V1 不引入投票、审批或实时协作编辑冲突处理。

## 5. AI 设计与输出约束

### 5.1 AI 的两个职责

| 工作流 | 输入 | AI 任务 | 输出 |
| --- | --- | --- | --- |
| 内容结构化 | 用户图片/文字/链接 + 可见元数据 | 分类、命名、提取标签和候选属性 | 待确认的灵感草稿 |
| 生活决策 | 用户条件 + 共享收藏候选 + 双方偏好 + 最近反馈 | 排序、组合、解释取舍 | 结构化菜单或活动方案 |

**不需要复杂 Agent**：V1 以 Go 服务端的候选筛选 + LLM 结构化输出 + 结果校验为主。

### 5.2 推荐策略

1. 默认优先使用已收藏内容，并保留其原始 `item_id` 方便回查。
2. 收藏不足或不匹配时允许提出新灵感，但清楚标记 `source=new_suggestion`。
3. 对于新增餐厅/活动，V1 不承诺实时存在性、营业状态、价格及位置真实性。无法验证时提供**类型或方向建议**，不伪造具体商户事实。
4. 推荐内容需满足硬约束：预算上限、人数、指定模式、明确饮食禁忌等；无法满足时说明条件冲突。
5. 每次推荐给出 1 个主方案和最多 2 个备选，避免无限罗列。
6. 「换一组」尽量降低与本轮已看方案的重复度。
7. AI 产生的标签、时间和口味判断可纠错；用户修改优先于模型推断。

### 5.3 输入信息（逻辑协议）

| 字段 | 说明 |
| --- | --- |
| `space_id` | 双人共享空间 |
| `scenario` | `food` / `play` |
| `mode` | food：cook / dine_out / surprise；play：outdoor / indoor / flexible |
| `demand` | 自然语言要求 |
| `constraints` | 预算、时长、人数、口味、出行偏好等 |
| `candidates` | 服务端检索出的收藏项（标识、类别、摘要、标签） |
| `preferences` | 双方明确保存的个人偏好 |
| `recent_feedback` | 最近已完成方案的评价，可选 |
| `excluded_ids` | 「换一组」时避免重复的候选 |

### 5.4 输出信息（逻辑协议）

| 字段 | 说明 |
| --- | --- |
| `scenario` / `mode` | 当前决策类型 |
| `title` | 方案标题 |
| `summary` | 一句话说明 |
| `recommendation_items[]` | 菜品 / 餐厅 / 活动等结构化组成项 |
| `source` | `saved` 或 `new_suggestion` |
| `source_item_ids[]` | 使用收藏素材时关联其 ID |
| `reason` | 为什么这样推荐 |
| `estimated_time` / `estimated_cost` | 可选估计值，标记估计性质 |
| `unknowns[]` | 未验证、执行前要确认的事项 |
| `alternatives[]` | 最多两个备选 |

**服务端必须验证**：JSON 结构、引用的收藏 ID、必填字段、预算/模式等硬性限制；模型不能直接修改数据库中的已保存方案。

## 6. 关键数据对象（概念模型，不是建表 SQL）

| 对象 | 作用 | 主要字段举例 |
| --- | --- | --- |
| User | 用户 | id、昵称、头像 |
| Space | 两人共享生活空间 | id、名称、创建人 |
| SpaceMember | 共享关系 | space_id、user_id、加入时间 |
| IdeaItem | 收藏灵感 | id、space_id、type、title、description、tags、image、source_url、metadata |
| UserPreference | 个人偏好 | user_id、space_id、口味、忌口、活动偏好 |
| Decision | 一次 AI 决策生成 | id、space_id、scenario、conditions、result、created_by |
| Plan | 已采纳或待用方案 | id、decision_id、status、adopted_by、created_at |
| Feedback | 实际完成反馈 | plan_id、user_id、rating、comment |

类型可选：`recipe`、`dish`、`restaurant`、`activity`、`todo`。  
**内容区别**：`recipe` 是家里能做的菜谱；`dish` 是某一道菜（可关联餐厅或菜谱）；`restaurant` 是就餐场所。不要把三者混成一张「菜单」概念。

图片建议存对象存储，业务库只存资源地址/标识；结构化拓展属性可使用 JSONB，关键筛选条件宜单独建列或索引。

## 7. 页面状态与异常处理

| 情况 | 页面行为 |
| --- | --- |
| 灵感库为空 | 引导先添加 3～5 个灵感；也允许尝试 AI 新建议，但明确效果有限 |
| AI 识别失败 | 保留原始输入，允许编辑标题和类型后直接保存 |
| AI 推荐超时/失败 | 保留需求与筛选条件，提示重试，避免重复保存 |
| 收藏与需求不匹配 | 说明匹配不足，展示可用收藏或探索型新建议 |
| 无真实地点信息 | 标注「位置/营业信息待确认」，不提供虚假导航 |
| 两人偏好冲突 | 给折中推荐与简短解释，不擅自改写个人偏好 |
| 保存重复点击 | 前端禁用重复提交，后端基于请求 ID 实现幂等 |
| 删除被历史方案引用的收藏 | 历史方案保留生成时快照，不因原始收藏删除而失效 |
| 网络断开 | 提示失败及重试；不要展示未成功持久化的成功状态 |

## 8. 非功能需求与工程边界

- **权限**：所有读取、修改必须校验用户属于相应 `space`；不能只依赖前端传入空间 ID。
- **隐私**：用户上传图片、生活偏好、共享历史只用于授权场景；明确告知图片将交由模型服务处理，避免记录不必要的敏感信息。
- **密钥管理**：模型 API 密钥只放 Go 服务端，不写进小程序或 Web 客户端。
- **性能**：普通灵感列表保持快速响应；AI 请求需要 loading、取消/重试入口，避免阻塞页面其他操作。
- **可靠性**：保留推荐请求及错误日志、模型耗时和失败率；推荐失败不影响灵感库 CRUD。
- **成本**：先做候选检索再调用模型；图片压缩、长度限制和调用频率限制；不把整个收藏库无差别发送给模型。
- **架构**：V1 单体 Go 服务即可；暂不引入 MQ、微服务或复杂 Agent，除非真实瓶颈证明必要。

## 10. MVP 验收标准

### 10.1 功能验收

- [ ] 两个成员可以进入同一个共享空间，看到彼此收藏的内容。
- [ ] 可以通过文字、图片或链接新增灵感，且支持编辑、删除与分类筛选。
- [ ] 图片录入时 AI 提供可编辑草稿，识别失败仍能手动保存。
- [ ] 「自己做」能够根据收藏菜谱及约束搭配一套菜单。
- [ ] 「出去吃」能够从收藏餐厅/菜品中推荐，并合理标注新建议。
- [ ] 「帮我选」能够比较做饭与外出吃饭。
- [ ] 「玩什么」能够生成符合时间/预算的活动组合；待办只按需加入。
- [ ] 能换一组、采纳方案或保存以后再做。
- [ ] 能查看待用和已完成方案，完成后做简单反馈。
- [ ] 推荐的新地点不会伪装成已核实的实时商家信息。

### 10.2 真实使用验证

建议前期由两位真实用户录入约 20 条素材（例如菜谱 6、餐厅/菜品 6、活动 6、待办 2），分别完成吃饭、约会决策各至少 3 次；记录：

- **有效录入率**：保存时 AI 草稿是否基本正确，需要多少手工修正。
- **推荐采纳率**：实际采纳的推荐次数 / 有效推荐次数。
- **完成率**：完成方案数 / 已决定执行方案数。
- **重复使用意愿**：下个周末是否主动再次使用。
- **决策耗时**：从发起推荐到确认选择需要多久。

以上是 MVP 观察指标，不预设未经实测的达标数值。

## 11. 开发顺序与版本计划

| 迭代 | 交付范围 | 验收重点 |
| --- | --- | --- |
| V0：交互 Demo（已有） | 首页、决策、灵感库、新增、记录等静态/本地模拟交互 | 明确导航和操作流 |
| V1.1：真实数据 | 双人空间、灵感 CRUD、图片/链接保存 | 两人能持续积累素材 |

不建议为追求单周上线省略登录权限、数据隔离与错误处理。若时间不足，应先减少高级推荐条件，而不是牺牲这几项基础保障。

## 12. 确定的产品决策

1. **核心场景**：吃什么与玩什么都进入 V1。
2. **吃什么**：包括自己做、出去吃、帮我选；可收藏菜谱、具体菜品和餐厅。
3. **灵感输入**：文字、图片/截图、链接；AI 辅助识别，用户确认保存。
4. **推荐范围**：优先收藏，允许 AI 补充新建议，但 V1 不承诺实时地点数据。
5. **双人机制**：共享灵感库，任何一人可独立决策，不做投票审批。
6. **推荐后管理**：只保存方案、状态、完成反馈，不做复杂计划管理。
7. **待办定位**：辅助推荐素材，而非独立完整任务管理系统。
8. **技术策略**：先采用可控 AI Workflow，不引入复杂 Agent 或微服务。

## 13. 后续需要在设计阶段细化的内容

- **页面级交互稿**：移动端信息层级、空态、加载态、错误态及推荐卡片细节。
- **字段与约束**：菜谱、菜品、餐厅、活动、待办的专属字段以及哪些允许为空。
- **AI 提示词与评测集**：包括菜谱识别、双方偏好冲突、预算限制、无收藏与幻觉检查。
- **后端接口合同**：灵感 CRUD、图片上传、推荐、采纳、状态与反馈。
- **微信小程序交付约束**：登录、域名白名单、图片上传和模型数据处理说明。

**最终产品原则**：用户不需要研究一个 AI 系统如何工作。日常随手收藏；需要决定时一句话提出要求；系统给出明确、可执行、解释得通的选择。

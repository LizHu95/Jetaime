# 历史向量化与增量记忆（M1）

本阶段实现历史片段检索、结构化记忆、增量处理和最小内部检索方法。正式群聊主 Agent 首次模型调用只使用有预算限制的近期上下文；需要补充历史事实时才调用 `answer_question` 执行混合检索与原文回查。本期不引入 Rerank、提醒或主动介入。主 Agent 与工具边界见[设计问答](主Agent设计问答.md)。

## 处理链路

```text
PostgreSQL 原始消息（群内 seq）
  → 发现群并记录首次回填水位
  → 租约抢占一个群的消息批次 + 最多 3 条旧消息作上下文
  → LLM 提取候选 → 持久化候选检查点
  → 候选 Embedding（内容哈希缓存）
  → 按人物/类型/事件/时间范围过滤，向量召回相关旧记忆
  → 完全重复直接 NOOP；其他相关项交给 LLM 消解
  → 事务写入历史片段、记忆版本、来源、向量任务并推进游标
  → 独立 Embedding Worker 处理持久队列
```

历史片段按时间邻近（20 分钟）、最多 12 条和约 4500 字节拆分；单条较长消息保持完整。每批最多读取 43 条原始消息，文本预算 18000 字节；优先丢弃可选 overlap，避免长消息阻塞。AI 消息只推进水位，不作为人类事实索引。原始消息只有 user/assistant 两种，无额外系统消息。

首次记录 `backfill_end_seq`，水位之前无需等待阈值。追上后任意条件满足即处理：15 条未处理用户消息、聊天空闲 5 分钟、最早未处理消息等待 30 分钟。5 秒扫描一次，最多每分钟发现新群并补偿扫描向量队列。

## 数据和恢复保证

新增迁移：`000008_memory.up.sql`，不修改已有迁移，不重建数据库。

| 表 | 持久状态 |
| --- | --- |
| `memory_progress` | 每群独立 seq 游标、首次回填水位、pipeline 指纹、租约令牌、失败重试 |
| `memory_batches` | 已完成提取的候选、逐个消解结果检查点，以及批次是否提交 |
| `memory_documents` | 历史片段、记忆逻辑 ID、修订版本、当前状态、时间范围 |
| `memory_document_sources` | 同群原始消息外键、可回查的证据关系 |
| `memory_embeddings` | 模型版本、维度、内容哈希、pgvector 向量、任务与重试状态 |

- **部署/重启不重置游标、不重算 ready 向量。** 无新消息时不调用提取模型。
- 提取完成并保存检查点后，中断重启复用候选；逐个消解结果也保存检查点，重启跳过已经完成的候选；向量完成并保存后，复用向量。
- 候选文本直接成为正式记忆时复用同一向量；消解后文本改变才排队生成新的向量。
- 批次的历史片段、记忆修改、任务入队和游标在一个事务中提交，失败全部回滚。空候选也推进游标并建立历史片段索引。
- 每群同一时间只有一个有效批次租约（5 分钟，单次处理最长 4 分钟）；过期 Worker 不能提交。Embedding 任务单独使用 2 分钟租约和 60 秒 HTTP 超时。
- 失败保留任务，按次数退避（30 秒至 10 分钟），处理状态持久化错误；不会因失败跳过消息。
- **外部模型调用无法承诺严格一次。** 模型已返回、尚未保存时崩溃，恢复后可能再次调用；已成功保存的步骤不重复处理。
- `-memory-backfill` 跳过触发阈值，但仍遵守游标、检查点和租约，是“继续回填”，不是“清空重建”。存在租用中/等待重试的数据时退出报错，可稍后重跑。
- 模型、模型修订、向量维度、提取模型身份或 pipeline 版本变更时，已有 pipeline 不匹配会拒绝启动处理。可用 `-memory-check -memory-config <配置路径>` 只读检查兼容性；部署会在替换文件和停止进程前检查。**本阶段不提供自动模型升级/重建命令**；升级须另行设计版本化回填和切换，不能删游标来解决。

## 记忆与权限边界

- 本期仅从当前双人群聊天提取**群共享记忆**；subject 表示记忆涉及的人物或 shared，不表示私人可见性。未接入私人聊天或跨群用户画像。
- 类型包括 preference / decision / plan / fact / constraint / event。记录 enduring / temporary / event 时间范围与具体事项标识。
- ADD 新增；NOOP 只补证据；UPDATE 留下旧版并建立新版；INVALIDATE 留下取消记录并停用旧版。
- 修改和取消必须显式变更，且旧记忆人物、类型、事项标识、时间范围完全匹配；相似度不能直接覆盖。
- 同批次同一身份/事项只允许一个最终候选，来源至少包含一条新消息；旧消息 overlap 不能单独产生重复候选。模型返回仅引用本批次已知历史用户消息的候选时，提取器忽略该候选，避免整批因重复提取而反复失败；本批次的新候选与原始历史片段照常保存。未知来源、AI 来源和缺失来源仍保留给严格校验并拒绝。来源归属由应用校验、同群外键兜底。模型语义判断仍需真实案例评测。
- 每条检索 SQL 均校验群成员与群状态；向量查询先鉴权再调用外部模型，返回前再次鉴权。
- 现有产品关闭群而不支持成员退出；关闭群事务清理所有派生记忆、检查点和向量，原始聊天按现有规则保留。派生写入与关闭串行，旧 Worker 无法回写。
- 删除原始证据会撤回相关派生版本、对应向量及候选检查点，并使未完成租约失效；不回退已完成游标。其他仍存在的历史不会因此全量重算。消息编辑目前被数据库明确拒绝，后续支持编辑时需提供显式重建流程。

## 模型配置与部署

配置模板：`services/api/config/memory.example.json`。**正式 API 启动时自动启动记忆处理与向量 Worker，没有 enabled 配置开关。** Embedding 为 `qwen3.7-text-embedding-flash`、1024 维，extraction 为 `qwen3.7-flash`，独立于主 Agent 的聊天模型；模板的区域 URL 仍占位，需要替换为真实地址。配置或密钥缺失时启动报错，不静默跳过处理，不生成假向量。

1. 复制模板到 `local/memory.json` 并填写真实区域 URL；本项目本地配置已使用现有云模型的连接地址。
2. 数据库主机安装 pgvector；迁移要求扩展位于 `public`，执行迁移的账号需要创建扩展的权限，或 DBA 预先执行 `CREATE EXTENSION vector WITH SCHEMA public`。
3. Embedding 使用 `qwen3.7-text-embedding-flash`，固定为默认 1024 维，运维 revision 初始为 `v1`。启用前填写所在区域的真实 URL 和密钥环境变量，核对输入字节预算。revision 是由运维固定的向量空间版本标识，不是额外发送给 API 的参数；模型本身仍应尽可能固定版本。
4. extraction 默认使用 `qwen3.7-flash`，与主 Agent 模型配置独立，聊天可继续使用 Max；核对所在区域的真实 URL，切换聊天模型无需同步更改 extraction。当前该模型同时负责候选提取和必要时的记忆消解（ADD / UPDATE / NOOP / INVALIDATE）；没有相关旧记忆或完全重复时，不额外调用消解模型。建议起始上下文 32768；所有 LLM 请求保留输出预算并在调用前校验。`max_input_bytes` 至少为 `18000+2048`，也必须符合实际 Embedding 模型的输入能力。
5. 无需额外开启功能，启动会校验配置与密钥并启动 Worker。旧配置中的 enabled 字段应删除；当前解码器会拒绝未知字段。迁移命令与仅健康检查/本地调试台模式不启动记忆处理。

本地回填（会加载 `local/.env`，需提前迁移）：

```sh
make memory-backfill
```

服务启动可显式指定 `-memory-config /absolute/path/memory.json`，或设置 `JETAIME_MEMORY_CONFIG`。未指定时优先读取工作目录的 `memory.json`，再读取 `../../local/memory.json`，因此本地 `make dev` 自动加载本地记忆配置。

构建要求 `local/memory.json` 存在，自动打包该配置与 `memory.example.json`。服务器 `start.sh` 自动使用旁边的 `memory.json`，环境变量可覆盖路径。

```sh
bash start.sh migrate
bash start.sh memory-backfill  # 可选；常驻 Worker 也会自动继续历史回填
bash start.sh restart
```

`memory-backfill` 不启动 HTTP 或主 Agent，也不需要主 Agent 的模型配置。正常 API 启动已经会自动处理历史与新增消息，手动回填只是立即处理积压数据并退出。部署包不包含数据库或处理状态，部署和重启不重置游标或检查点。

Embedding 使用百炼兼容的 `/embeddings` JSON 接口（float 输出），不固定具体模型；本期不加 Rerank，pgvector 使用精确余弦检索，不提前固定 ANN 索引的维度。

接口依据：[百炼 Embedding 接口](https://help.aliyun.com/zh/model-studio/embedding-interfaces-compatible-with-openai)、[pgvector](https://github.com/pgvector/pgvector)。

## 内部检索契约

memory 不注册 HTTP 路由。QA 工具通过 `Service.Search(ctx, groupID, actorID, SearchInput)` 在进程内调用；群组与用户身份由可信调用方传入，内部仍检查成员身份及群状态。

下面是 SearchInput 的字段示意：

```json
{
  "query": "杭州",
  "limit": 5,
  "kind": "decision",
  "subject": "shared",
  "since": "2026-01-01T00:00:00+08:00",
  "until": "2026-12-31T23:59:59+08:00"
}
```

仅 query 必填。limit 默认 5、最多 20。固定执行关键词与向量混合检索，不再接受 mode 参数；kind、subject、since、until 可省略。

- vector 使用配置中的同一向量空间；keyword 使用 pg_search 的 Jieba 中文分词与 BM25 相关性排序（匹配任一查询词），不再要求包含完整查询文本；hybrid 对两路各 Top20 进行 RRF 排序，不调用 Rerank。
- documents 返回文本、源消息 IDs、涉及人物、类型、时间范围、版本等；按消息查询接口可回查原文。历史片段保留当时发言者身份。
- 同时返回 cursorSeq、recentUnprocessed（游标之后最多最近 30 条用户消息，按时间正序）和 recentOmitted，覆盖尚未处理的新事实，不谎称包含全部近期记录。
- 结构化记忆已提交但向量尚未完成时，关键词查询仍可命中；向量查询需要相应任务完成。正式 API 要求记忆模型配置有效后才能启动。
- score 是 RRF 排序分，不是事实可信度。历史片段可能包含已改变的旧决定，QA 阶段必须根据时间和来源解释，不能把检索结果当正式任务状态。

QA 调用统一混合检索，传入服务端固定的 `MaxSeq=context_end_seq`，不允许模型覆盖群组、请求人或截止范围。检索排除任何来源超出截止的文档，近期未处理消息同样受截止限制；原文回查再次校验权限和 seq。QA 当前只检索 `kind=history`，取前 5 个片段、去重后最多 20 个来源 ID，通过 `SourceEvidence` 优先读取直接来源，再补前后各 2 个 seq 范围的消息；补读记忆游标后且尚未持有的最多 30 条用户原文，不再固定读取最近 40 条。最终最多 80 条，受模型预算裁剪；直接来源优先，其余背景按真实时间选取。摘要不直接作为回答证据，引用仅接受最终输入的原文 ID。群关闭或授权失效时查询失败。

处理水位、回填水位和失败原因保存在 `memory_progress`，向量积压保存在 `memory_embeddings`，通过数据库与 Trace 排查，不提供专门的状态 HTTP 接口。游标代表片段与记忆事务已提交，不代表所有向量已经完成。

## 主 Agent 按需检索

正式群聊每次 AI 提问及重试先在 `chat.build_context` 阶段加载当前问题、直接引用与最多 12 条/4 KiB 近期背景，保留提醒草稿、原提问时间和时区，不调用向量或关键词检索。主 Agent 对普通知识、闲聊和当前原文足够的问题通过 `respond` 直接回答；依赖历史且证据不足时才选择 `answer_question`，其内部按后端 `context_end_seq` 混合检索、回查原文并生成回答。时间段回顾走 `summarize_history`，不使用语义检索片段替代完整范围。

检索失败只影响需要检索的工具调用，不阻塞普通直接回答。检索仍按群成员权限和原提问截止范围取数，当前问题与直接引用固定保留，来源必须来自实际提供的原文。长期记忆的后台索引与提取 Worker 保持运行；本地调试台和离线评测没有数据库历史检索。

### 记忆诊断字段

- `memory.embedding` 始终记录输入字节数、调用用途（`search_query` / `memory_content`，直接调用为 `unspecified`）、配置与实际维度、返回条数、HTTP 状态（收到响应时）、成功状态及稳定失败原因码。Token 同时提供 `llm.token_count.prompt`、`llm.token_count.total` 与兼容字段 `memory.embedding_tokens`（成功解码响应时）。失败码区分空输入、输入超限、请求构造、传输、HTTP、响应解析、响应结构、维度、非有限值和零向量。
- `memory.validate_candidates` 记录 `memory.validation_stage`（`before_save_extraction` / `before_apply_mutations`）、批次序号范围、消息数、候选数、提取复用状态及校验结果；失败提供 `memory.failure_reason`，候选级失败另提供从 0 开始的 `memory.failed_candidate_index`。两个阶段保留原有校验行为。
- `JETAIME_TRACE_CAPTURE_CONTENT=true` 时，Embedding 输入正文与维度/数量摘要、候选校验输入与结果摘要写入 `input.value` / `output.value`，沿用 64 KiB 截断限制。关闭时仅记录诊断字段。完整向量、供应商错误正文和认证信息不写入 Trace。

### 记忆状态与适用日期

提取候选及正式记忆包含 `status`（`active/completed/cancelled/unknown`）、`validFrom`、`validUntil` 与 `changeType`（`none/supplement/modify/cancel/complete/correct`），不再输出 `explicitChange`。日期为 Asia/Shanghai 的 `YYYY-MM-DD`，未知必须输出 `null`；它们表示内容的适用区间，与来源消息时间 `startAt/endAt` 分开。无明确证据不能猜测日期或因时间过去就判定事项完成。

`completed` 适用于 plan/event，`cancelled` 适用于 plan/event/decision。`complete/cancel` 必须分别对应 completed/cancelled。完成或取消更新同一记忆的版本，仍可检索；`INVALIDATE` 仅允许 `correct`，用于撤回错误记忆。`UPDATE` 要求明确的非 none 变更。`NOOP` 及正文完全重复的快捷路径也必须核对状态与适用日期，避免丢掉纯元数据变化。新版本保存候选的状态、适用日期和变更类型。

迁移 `000017_memory_metadata.up.sql` 将存量文档状态设为 unknown、适用日期置空、changeType 设为 none，不对旧文本作推断。未完成批次检查点清除并使其租约失效，下次从现有游标重新提取；已完成的游标、记忆版本、来源和向量保留。部署时应先停止旧 Worker，再执行迁移并启动新版，避免旧协议继续写入。

### 关键词检索扩展依赖

迁移 `000018_memory_search.up.sql` 要求数据库主机已安装 ParadeDB `pg_search >= 0.26.0`（同时保留 pgvector）。迁移会启用扩展并为有效记忆创建 Jieba 中文分词索引；查询使用 `|||` 文本匹配和 `pdb.score` 排序，再与向量路进行 RRF 融合。群权限、人物、类型、来源时间和提问截止序号过滤仍在取 Top20 之前执行。扩展缺失或版本过低时迁移失败，不回退子串匹配。

索引会覆盖已有有效记忆，不需要重新提取或重新生成向量。当前迁移在事务中普通建索引，会阻塞该表写入；数据量大时应在维护窗口执行并预留索引构建空间。测试数据库同样需要安装该扩展。

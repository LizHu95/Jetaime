# 日常协同 AI 助理｜产品方案 V2.0

> 更新日期：2026-10-11  
> 状态：产品方向与 Demo 核心范围已确认；交互细节和视觉方案继续迭代。  
> 本文是当前产品方向的基线，不代表所述能力已经实现。

## 1. 产品定位与目标

一个融入成员日常聊天的 AI 协同助理。它结合当前对话与相关历史消息，理解成员的计划、偏好和约束，帮助创建与更新待办、回答问题，并提供几个合适的候选方案，辅助成员做出决定。

核心价值：减少反复翻聊天、重复沟通和遗漏事项，让成员更容易从“聊过了”走到“决定了、有人去做了”。

核心链路：**群组聊天 → 理解当前问题与相关历史 → 解答 / 提供候选 / 提取待办 → 成员选择或确认 → 个人与群组待办 → 完成与跟进**。

三个能力围绕同一段对话协同工作：聊天是入口与上下文来源，问答帮助找回信息，决策帮助形成选择，待办承接已经明确的行动。

### 与 V1 的关系

| 维度 | V1：情侣决策助手 | V2：日常协同 AI 助理 |
| --- | --- | --- |
| 产品入口 | 收藏、AI 决策、我的 | 群组聊天、我的规划；群组管理为辅助入口 |
| 核心信息来源 | 笔记收藏、长期偏好 | 当前对话、相关历史消息、已确认待办；必要时使用相关记忆 |
| 核心闭环 | 收藏 → 偏好匹配 → 推荐 → 反馈 | 讨论 → 解答 / 候选比较 → 确认行动 → 待办执行 |
| 协作对象 | 个人与情侣空间 | 群组与成员，双人日常属于群组的一种使用场景 |
| 决策候选 | 当前空间内已收藏内容 | 成员提供的候选，或 AI 生成的概念建议 |
| 待办规划 | 后续扩展 | Demo 核心能力 |
| 内容收藏与市场 | 原规划的重要部分 | 不作为 V2 Demo 的前置条件 |

## 3. Demo 范围

### 第一周本地版本

后续讨论已收敛第一周目标：固定用户和群组，直接处理短聊天历史，先完成历史问答与来源引用，再完成待办提取、确认保存、查看与完成。最小实体为 User、Group、GroupMember、Message、Task；消息历史由 Message 集合表达，不单独建 Memory。已落地最简 HTTP 调试页面与 JSON 文件存储。具体任务与七天验收见[开发任务清单](开发任务清单.md)。

下面保留完整群组 Demo 的范围；真实登录、邀请、实时聊天、自动介入和候选决策不属于第一周必交付项。

### 完整群组 Demo

Demo 用于验证成员是否能在聊天中自然获得帮助，并把讨论变成可执行的事项。

| 能力 | Demo 交付目标 | 边界 |
| --- | --- | --- |
| 群组 | 查看、创建、切换群组，邀请并确认加入，查看成员 | 群主 / 成员两种基础角色；复杂权限与组织管理后置 |
| 聊天 | 发送与查看文字消息，识别发送者和时间，保留历史 | 图片、语音、文件及复杂消息编辑撤回后置 |
| AI 解答 | 在群聊内提问，结合当前对话与相关历史回答 | 有历史依据时引用原消息；无依据时明确说明 |
| AI 决策 | 比较成员给定的候选，或提出几个概念候选 | 最多三个，不为了凑数量编造；实时商家核验不作为 Demo 前置能力 |
| 待办协同 | 从对话提出待办建议；确认、修改、手动创建、完成或取消 | 包含标题、负责人、计划时间、所属群组和来源 |
| 我的规划 | 汇总分配给自己的待办，按计划时间与状态查看，回到相关群聊 | 不在 Demo 中建立完整独立日历系统 |
| 可追溯性 | 解答、候选理由和提取事项能关联到来源消息 | 摘要可辅助定位，不能代替关键事实的原始证据 |

暂不纳入：笔记收藏市场、社区、公开分享、复杂重复任务、系统提醒推送、实时地图与商家搜索、自动读取微信个人聊天记录、复杂多 Agent 架构。

HTML 原型与可运行 Demo 分开验收：原型用于展示交互；可运行 Demo 还需验证真实消息持久化、成员权限、AI 调用、来源关联与待办写入。

## 4. 信息架构与页面职责

### 4.1 群组列表与管理

- 显示自己创建或加入的群组，进入时明确当前群组。
- 支持创建群组、发起邀请、被邀请者确认加入、查看成员。
- 创建者成为群主；普通成员可以聊天、向 AI 提问和参与待办协同。
- 邀请显示群组名称和加入对象，过期、重复加入或人数限制应有明确状态。
- 切换群组后，聊天、候选、待办建议和上下文随之切换。

### 4.2 群组聊天

聊天是产品主界面，承载普通消息、AI 回复、历史引用、候选卡片、待办建议和确认结果。

| 区域 | 职责 |
| --- | --- |
| 群组头部 | 群组名称、成员信息、邀请 / 群组详情入口 |
| 消息区 | 成员对话、AI 解答与协作卡片，展示发送者和时间 |
| 输入区 | 普通消息、@AI；可提供历史问答 / 辅助决策 / 整理待办快捷入口 |
| 辅助信息 | 当前群组待办与相关聊天共识，可通过面板或详情查看 |

AI 的回复应与成员消息明确区分。群组共识用于解释推荐依据，不能把本次临时条件自动写成长期偏好。

### 4.3 我的规划

- 汇总当前用户在各群组中负责的待办，不把所有群组待办当作本人任务。
- 展示事项、计划时间、完成状态、所属群组与来源。
- 支持查看全部待办、今天及其他计划时间、已完成事项。
- 支持修改、完成、取消，并回到相关群聊或来源消息。
- 负责人变更后，对应成员的个人规划同步变化；多人协作任务先以一个明确负责人为主。

原型中的“今天 / 明天 / 本周 / 待定”为体验示例。实际 Demo 需把可确定的时间解析成日期或时间，保留模糊表达；没有依据时不擅自补截止时间。

## 5. AI 介入规则

原则：成员可以自然聊天，AI 在被需要时参与；提出操作建议与实际执行是两个步骤。

| 情况 | 默认行为 | 示例 |
| --- | --- | --- |
| 普通闲聊 | 存储消息，不逐条回复 | “这周有点忙。” |
| 明确提问 | @AI 或快捷入口触发解答 | “@AI 我们之前说的预算是多少？” |
| 决策请求 | 整理条件，比较或生成候选 | “@AI 周末怎么安排？” |
| 明确行动 | 提出待办建议，等待确认 | “我明天负责订票。” |
| 讨论意向 | 不直接创建待办，必要时询问 | “要不要去露营？” |
| 修改 / 取消既有事项 | 展示对应事项与建议变更，确认后更新 | “订票改成周六吧。” |

默认不为每条普通消息调用模型。按需解答与决策、适当批次的摘要或行动识别，是后续实现评估的方向；具体策略需兼顾及时性、误触发与成本。

自动行动识别开关已经在原型中探索，但其最终交互及配置范围尚未确认。明确的修改或取消要对应已有待办，不能只生成一条同名新任务。

## 6. 三项核心能力

### 6.1 问题解答

区分两类问题：

1. **历史事实问答**：“之前说了什么？”以当前群组原始消息为依据，回答附发送者、时间和消息引用。
2. **一般问题解答**：“野餐需要准备什么？”可结合常识与当前计划作答，区分一般建议与成员确实说过的事实。

当前 Demo 优先验证历史问答。一般知识问答及是否接入外部检索，后续单独确定；涉及当前天气、价格、营业状态等信息时，不能把未核实内容当作事实。

摘要和相关记忆用于定位信息。找不到证据、信息冲突或原消息不可访问时，说明限制或追问，不编造历史。引用可跳回原消息。

### 6.2 辅助决策

支持两种候选来源：

- **成员给定候选**：“野餐、咖啡、在家做饭选哪个？”在给定集合内比较。
- **AI 生成候选**：“周末怎么安排？”结合上下文提出最多三个概念建议。

每个候选应说明：方案内容、为什么适合相关成员、主要取舍、需要进一步确认的信息。必要时补充预算与时间等关键条件，再给建议。

遵守明确硬约束。信息不足时说明不确定性，不把生成建议包装成已经核验的商家、价格或可预订方案。

AI 可以推荐，但推荐不等于成员已决定。候选选择与最终执行确认由成员完成；多人选择不同方案时保留分歧，不能让一个成员的点击自动代表全体同意。多人一致性规则与是否需要投票，后续明确，Demo 不提前引入投票系统。

选择方案后，可提出相应待办建议，不自动分配未确认任务。一次拒绝不自动沉淀为长期偏好。

### 6.3 待办提取与协同

流程：**识别行动 → 待办建议 → 确认 / 修改 / 忽略 → 创建 → 规划展示 → 完成 / 取消**。

| 字段 | 规则 |
| --- | --- |
| 标题 | 简洁表达具体行动，不把整段对话直接当作标题 |
| 负责人 | 根据明确表达识别；“我”对应消息发送者；不明确时等待选择 |
| 计划时间 | 识别明确日期 / 时间，模糊时间保留为待确认；无时间允许待定 |
| 所属群组 | 来自当前对话，不自动跨群组共享 |
| 来源消息 | 关联提取依据；手动创建标记为手动来源 |
| 状态 | 待完成、已完成、已取消；未确认建议与正式待办分开 |

任务由成员确认后写入，避免把讨论意向当成承诺。同一事项重复提取或失败重试不能重复创建。变更标题、负责人、时间或取消事项时，展示拟变更对象与结果。

Demo 默认允许群组成员在群内提出任务、确认分配，并管理本人负责的任务；修改他人已确认任务的权限与确认机制需在实现前明确，不能仅凭模型建议执行。

## 7. 贯穿 Demo 的场景

使用虚构消息与成员验证，不以真实私人聊天作为默认测试资料。

| 步骤 | 场景 | 预期结果 |
| --- | --- | --- |
| 1 | 林一创建群组“我们的日常”，邀请小夏 | 小夏确认加入，双方进入同一群聊 |
| 2 | 小夏说想出去透气；林一说两人预算 200 元以内；小夏说离家近、周日晚回家 | 普通聊天正常呈现，保留可引用的原始消息 |
| 3 | “@AI 我们之前说的预算是多少？” | 回答 200 元以内，并引用预算原消息 |
| 4 | “@AI 周末有什么合适的安排？” | 提供公园野餐、散步 + 咖啡、在家做饭等概念候选，解释取舍 |
| 5 | 成员表达选择野餐 | 记录选择；必要时继续协调其他成员的意见 |
| 6 | “我明天负责确认地点和准备午餐。” | 提出对应负责人、时间与来源明确的待办建议 |
| 7 | 确认或修改建议 | 创建一次正式待办，在群组待办与负责人“我的规划”中展示 |
| 8 | 查看规划，完成或调整事项 | 状态与负责人视图一致，可回到原群聊 |
| 9 | 创建另一个群组 | 新群不能读取前一个群的消息、私有上下文与待办 |

这一场景验证讨论 → 解答 → 决策 → 行动的完整体验。最初的验证顺序仍以聊天和适时解答为先，再串联候选与待办。

## 8. 关键状态与异常体验

| 状态 | 产品行为 |
| --- | --- |
| 空群组 | 展示邀请成员与开始聊天入口，不显示虚构历史 |
| 消息发送失败 | 保留输入或失败消息，支持重试；不能显示已送达 |
| AI 处理中 | 明确正在处理，防止重复请求；普通聊天仍可继续 |
| AI 失败 / 无历史证据 | 说明失败或证据不足，保留问题，可重试或补充信息 |
| 候选条件不全 / 冲突 | 追问关键条件或说明冲突，不强行推荐 |
| 待办缺负责人 / 时间 | 负责人待选择；时间可待定，不替成员擅自承诺 |
| 待办写入失败 | 保留建议和修改输入，重试不重复创建 |
| 群组切换 | 当前上下文随群组切换，晚到回复回到原群组，不覆盖新群组结果 |
| 权限失效 / 来源不可见 | 停止使用不可访问上下文，明确提示来源不可查看 |
| 多人修改冲突 | 保留本地输入，展示最新状态，避免覆盖他人变更 |

## 9. 历史、上下文与隐私边界

- 群组是对话与协同数据的基础边界。AI 只使用当前用户有权访问的当前群组消息与相关任务，不默认混入其他群组或私人记忆。
- 原始消息保留发送者、时间与稳定标识，支持回答引用、待办来源与变更追溯。
- 最近消息、摘要、相关历史和必要待办状态可共同构成上下文；实现不必把全部历史一次性发送给模型。
- 区分成员个人偏好、共同约束和本次临时计划；不从一次行为推断永久偏好。
- 长期记忆作为支撑能力，若引入须提供查看、纠正与删除；完整记忆页面不作为本次 Demo 的必需主入口。
- 成员加入前的历史是否可见、退出后能否访问既有任务、删除消息对引用的影响，均须在真实多人 Demo 开发前明确。
- 私人对话导入需获得相关成员同意；默认使用脱敏或虚构资料，不把真实聊天及敏感 Trace 提交到仓库。

## 10. 验收与实现顺序

### Demo 验收

- 两个成员能创建 / 加入同一群组，发送并查看消息；可创建另一个群组验证隔离。
- 普通聊天不会引发连续 AI 打扰；明确请求能触发对应解答。
- 历史问答能够引用原消息，缺少依据时如实说明。
- 决策支持给定与生成两种候选来源，结果有理由、取舍与未知信息。
- 明确行动形成待办建议，成员可确认、修改或忽略；确认后进入负责人规划。
- 修改负责人、计划时间、完成或取消后，相关视图一致；重复处理不产生重复任务。
- 消息、任务与来源可以在重新进入后恢复，不以浏览器临时状态代替正式持久化验收。
- AI 失败不阻塞普通聊天和既有待办管理。

### 建议实现顺序

| 阶段 | 目标 |
| --- | --- |
| 1：核心链路验证 | 用静态消息回放验证上下文、历史问答、触发策略与来源引用 |
| 2：协同能力验证 | 加入待办提取 / 确认 / 更新，以及两种候选决策，验证重复处理与失败重试 |
| 3：可运行群组 Demo | 接入成员与邀请、真实聊天持久化、群组隔离和我的规划 |
| 4：真实使用反馈 | 用小范围实际使用调整 AI 介入时机、候选解释和待办确认体验 |

这是完整产品的建议顺序。第一周本地版本已单独拆解为[开发任务清单](开发任务清单.md)，以历史问答和待办为优先，不要求完成全部阶段。[第一周技术方案](技术方案.md)已记录本地版本的选型建议；完整多人产品架构仍待制定，任务与 V1 实现状态分别记录。

## 11. 原型与后续讨论

[HTML 交互原型](prototypes/daily-collaboration-demo.html)用于讨论群组聊天、历史问答、候选选择、待办确认与个人规划。它使用浏览器本地存储，AI 回复和成员加入为模拟行为，不代表已接入真实模型或多人服务。

原型目前仍在调整，视觉效果尚未获得认可。颜色、插画、布局、具体文案以及群组信息面板不作为已确认设计；历史截图只代表当时页面，不作为验收依据。本次先冻结产品方向与 Demo 核心范围，视觉以后继续迭代。

下一轮需要明确：

1. AI 主动介入的判断标准，以及是否默认开启行动识别。
2. 多人选项分歧如何协调，谁能确认最终方案和分配任务。
3. 群组人数上限、邀请有效期、新成员历史可见性与退出规则。
4. 任务时间精度、他人任务修改权限及取消机制。
5. 正式客户端是否继续沿用 V1 的微信小程序方向，以及 V2 技术实现与迁移范围。

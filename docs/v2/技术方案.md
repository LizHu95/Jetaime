# 日常协同 AI 助理｜V2 第一周技术方案

> 更新日期：2026-10-11  
> 状态：已按用户最新要求实现本地 HTTP 调试台，入口与运行限制见 [运行说明](运行说明.md)。  
> 范围：一周内本地运行，先历史问答与来源引用，再待办提取、确认保存与完成。

依据：[产品方案](产品方案.md)、[开发任务清单](开发任务清单.md)。本文针对第一周本地版本，不提前搭建完整群组聊天系统。

## 1. 技术选型

| 层级 | 第一周建议 | 选择理由与边界 |
| --- | --- | --- |
| 语言与模块 | 现有 Go 模块 | 沿用 `services/api`，无需引入第二套后端；工具链版本沿用仓库 `.go-version`，不在本轮升级 |
| 运行入口 | 统一 `cmd/api` HTTP 服务 | 内嵌最简 HTML 调试页面；当前唯一调试入口，在 8081 运行 |
| 模型运行 | 本地 Ollama | 已有接入经验，可记录真实输入输出；模型地址和标签可配置 |
| 模型选择 | 先试仓库现有默认 `qwen3.5:9b` | 这是代码当前默认值，不是对该模型效果的保证；以本机实际可用模型和小样本质量 / 耗时验证为准，不先进行广泛模型选型 |
| 调用方式 | Go `net/http` 调用 Ollama `/api/chat` | 直接控制超时、请求和错误；无需新增 SDK 或 Agent 框架 |
| 模型输出 | 两套 JSON Schema + Go 解码与业务校验 | 历史问答与待办提取分别约束；Schema 不代替来源、成员和确认规则 |
| 上下文 | 当前群组的短历史直接传入 | 保留消息 ID、发送者、时间、正文；不做 Embedding、RAG 或长期记忆 |
| 存储 | JSON fixture + 本地 JSON 消息与任务文件 | 原始 fixture 只读，模拟消息与任务状态独立保存；限定单进程写入；后续有并发或查询需求再评估数据库 |
| 日志与评测 | 本地 JSONL 运行记录 + Go 测试 + 人工语义核对 | 先保证可复现；当前使用本地步骤轨迹，不依赖 Phoenix / OTel |
| 页面 / HTTP | Go 标准库 + 内嵌 HTML / CSS / JS | 按本轮要求纳入最简 Demo；页面可模拟消息、显式触发和查看完整轨迹 |

Ollama 原生 Chat API 接受历史消息及 Schema，返回完成状态、Token 和耗时字段；建议第一版关闭流式输出，读完整结果后校验。[Chat API 官方文档](https://docs.ollama.com/api/chat)

Ollama 支持通过 `format` 传入 JSON Schema，官方也建议在 Prompt 中呈现结构要求。约束输出形状不代表事实正确或业务规则通过。[结构化输出官方文档](https://docs.ollama.com/capabilities/structured-outputs)

## 2. 七个核心职责

这是职责划分，不要求建七个独立服务、七个包或完整分层框架。

| 核心 | 负责什么 | 不负责什么 | 对应任务 |
| --- | --- | --- | --- |
| 领域数据 | User、Group、GroupMember、Message、Task，以及问答结果和待办建议类型 | 不把每个类型都做成 CRUD API；不新增 Memory 实体 | V2-01 |
| 上下文组装 | 检查模拟成员、按群组取消息、稳定排序、保留元信息；提取时加入相关已确认任务 | 不跨群组读取，不自动摘要或生成长期偏好 | V2-02 |
| 模型调用 | 模型配置、HTTP、超时 / 取消、Schema 请求、响应解码、调用指标 | 不判断成员权限，不直接写任务 | V2-03 |
| 历史问答 | 专用 Prompt / Schema、回答状态、来源 ID 验证、展示原消息 | 不用一般知识替代历史证据；不把合法来源 ID 当作语义正确的保证 | V2-04、05 |
| 待办提取 | 专用 Prompt / Schema、识别行动与意向、负责人和时间、待办建议 | 不自动把建议变成正式任务，不替成员承诺 | V2-06 |
| 确认与持久化 | 修改 / 忽略 / 确认建议、程序生成 Task ID、确认去重、文件保存、本人待办和完成 | 不依赖模型执行写入，不宣称支持多人并发事务 | V2-07、08 |
| 评测与观测 | 输入输出、模型 / Prompt 版本、耗时、错误、真实评测与固定替身测试 | 不把协议测试通过当作模型效果通过 | V2-09、10 |

HTTP 与页面只作入口，调用同一套 Workflow 与存储逻辑，业务处理不全部写在 `main.go` 中。

## 3. 两条流程与共享底座

```text
页面问答请求
  → 检查成员 + 组装当前群组历史
  → 问答 Prompt / Schema
  → 模型调用
  → 校验输出与来源
  → 展示答案 + 原始消息

页面提取请求
  → 检查成员 + 组装历史与相关已确认任务
  → 提取 Prompt / Schema
  → 模型调用
  → 校验建议、成员与来源
  → 用户修改 / 确认 / 忽略
  → 确认去重 + 保存 Task
  → 查看本人待办 / 标记完成
```

共享底座为领域数据、上下文读取、模型调用、校验基础与观测。两条流程保持独立，第一周不做自动 Intent Router；用户通过按钮或发送后明确配置触发，降低调试难度。

## 4. 模型与程序的边界

模型负责理解含义：问题需要哪些证据、行动是否明确、谁表达了行动、时间表达是什么。程序负责确定性处理：来源 ID 是否真实、是否属于输入群组、负责人是否有效、是否确认、是否重复、保存是否成功。

历史消息作为业务数据传入，不作为系统指令；群组成员的文字不能修改系统规则。多人对话保留真实 senderId，不把所有成员都转成同一个人的聊天历史，也不把成员消息伪装成 AI assistant 角色。

来源校验至少包含：来源属于本次输入、所在群组正确、ID 未伪造。引用显示正文、发送者与时间。语义是否受引用支持仍要人工评测，不能用 ID 校验替代这一检查。

时间识别优先让模型返回时间原表达及来源，程序根据源消息的日期和时区处理可确定的相对时间。歧义留待确认，任务允许 dueAt 为空。

上下文包含系统规则、Schema、历史和问题，应为输出预留容量。第一周限定短资料，设置保守输入上限；字符 / 字节估算不等于精确 Token 计数。调用后的 Token 记录用于校准，不能事后宣称已经证明输入未截断。若不能保证某份资料完整输入，拒绝该资料或要求缩小范围，不偷偷丢弃历史。

## 5. 本地数据与可靠性

- 虚构 fixture 保存用户、群组、成员关系和原始消息，可提交到仓库；输入校验 ID 与引用关系。
- 已确认任务、完成状态与 confirmationKey 存入同一个状态文件，避免只写任务却漏写去重信息。
- 建议在当前提取批次内保留，确认键由程序生成，不由模型决定。重复确认及重启后重复确认不重复创建；重新提取同一事项的语义去重单独验证。
- 单进程下串行写入，先把新状态写入同目录临时文件，再替换正式文件，成功后才更新内存状态或显示成功。
- 临时写入、关闭与替换错误都需处理；JSON 损坏时明确报错，不自动当空库覆盖。该方案不等同于数据库事务、跨进程锁或断电不丢数据保证。
- `os.Rename` 的行为有平台差异；本机替换行为需验证，不将一种平台的原子性假设推广到所有平台。[Go os 官方文档](https://pkg.go.dev/os#Rename)
- 运行任务文件、真实聊天与原始模型输出放在已被忽略的 `services/api/data/` 中；fixture 使用虚构或获授权的脱敏资料。

## 6. 仓库复用与代码组织

当前代码位置：

```text
services/api/
├── cmd/api/          # 本地 HTTP 调试服务入口
└── internal/assistant/    # V2 领域、上下文、问答、提取与确认流程
local/data/
├── chat-history/          # 用户导入聊天，Git 忽略
├── assistant/             # 本地运行状态与日志，Git 忽略
└── evals/                 # 私有评测输入、冻结版本与结果，Git 忽略
```

按实际实现创建，不预建空目录。`internal/assistant` 可先按文件划分职责，不需要为了分层新增大量接口。

一期的 `decisions.Provider`、Ollama 适配、调试台与遥测代码已移除。当前 V2 模型调用集中在 `internal/llm/`，使用 Eino 的 Ollama / OpenAI 兼容组件；保留 UUID、飞书 SDK 和共用 Go 检查工具。

已有 UUID 依赖可复用生成正式 ID。存储读取与写入应集中，避免业务流程直接到处操作文件。模型边界可以留一个小接口供替身测试，暂不建设插件化 Provider 注册系统。

## 7. 第一周不需要的设施与升级条件

| 设施 | 现在暂缓的原因 | 重新评估的触发条件 |
| --- | --- | --- |
| PostgreSQL / ORM | 单进程、少量资料先验证链路 | 真正多人写入、事务和复杂查询需求出现 |
| 向量库 / Embedding / RAG | 短历史完整输入足够 | 历史超容量，或有证据表明检索能改善成本与效果 |
| 长期记忆与增量摘要 | 会引入纠正、更新、遗忘与来源管理 | 跨时间使用稳定偏好，或长历史反复调用成本明显 |
| LangChain / LangGraph 等编排框架 | 当前是两条明确流程，不需要动态工具循环 | 出现多步工具执行、状态恢复和动态分支需求 |
| Redis / 消息队列 / WebSocket | 当前不是真实多人聊天服务 | 实时同步、后台任务或并发规模出现 |
| React / Taro 客户端 | 第一周重点是模型与业务闭环 | 最简页面验证通过，需要完整交互与多人使用 |
| Phoenix 强制部署 | 本地运行记录足以完成首次追溯 | 需要跨运行可视化、实验对照，或已有实例可直接复用 |

## 8. 判断是否跑通

技术跑通：真实模型返回结构化结果；原消息能追溯；不确定信息不擅自补全；待办经确认后创建；完成与去重状态重启可恢复；模型与文件错误不产生假成功。

质量验证：历史答案受来源支持，提取不把意向当承诺，负责人 / 时间正确；记录失败样本。暂不采用模型自报 confidence 作为可靠性证明。

使用价值：另一位成员是否愿意再次使用，以及回答或待办是否减少一次翻聊天、重复询问或遗漏。技术选型服务于这两类验证，暂不提前为完整产品规模设计。

# 主 Agent 核心设计问答

更新日期：2026-10-19。

本文记录群聊主 Agent 的核心策略、当前代码边界与后续扩展方向，作为新增能力时的设计依据。文中的“当前实现”依据仓库代码，不代表线上已经部署；“设计方向”表示已讨论确定、但尚未全部实现的目标。

记录时工作区正在将旧 `internal/assistant` 拆分为 `internal/ai` 与独立调试台。本文以功能契约为主，代码链接采用新的职责目录；目录迁移本身不视为运行链路已完成联调或部署的证明。

关联文档：[双人群聊接口](双人群聊接口.md)、[Workflow 评测说明](Workflow评测说明.md)。第一周的本地调试台设计见[技术方案](技术方案.md)，其手选能力流程不作为当前群聊主入口的设计依据。

## Q1：当前采用什么总体策略？

**设计方向：先采用一个主 Agent，加工具和按需加载的 skill；有独立决策需求后，再拆子 Agent。**

- 主 Agent 理解当前请求，直接回答或澄清，决定是否调用能力，并组织最终回复。
- 工具执行边界明确的操作，例如历史检索、待办提取。工具内部可以有固定流程和多次模型调用。
- skill 提供任务规则、证据要求和执行流程，按需加载给主 Agent。

不以代码量、模型调用次数或能力数量作为拆分子 Agent 的直接依据。

## Q2：主 Agent 当前负责什么？

**当前实现：默认在一次模型调用中直接回答或澄清；明确的待办提取请求进入专用提取流程。**

主 Agent 使用专用提示词与结构化输出，职责包括日常建议、知识解释、写作、理解近期对话、回答有证据的群聊事实，以及说明证据不足。迁移前版本为 main-v1，拆包中的版本为 main-v2-single-agent，具体版本随 Prompt 维护。

模型返回两类决策：

| action | 当前处理 |
| --- | --- |
| `answer` | 本次输出包含完整答案，由程序校验后保存 |
| `extract` | 加载提取上下文，执行既有提取 Workflow |

入口为 [`Agent.ExecuteMain`](../../services/api/internal/ai/agent/main/main_agent.go)。普通问答没有额外的意图分类模型调用，也不会先转交 help 或 QA 子 Agent。

## Q3：日常问答和历史问答需要拆成两个 Agent 吗？

**设计方向：两者属于主 Agent 的问答能力，采用不同的上下文策略和证据规则，通过 skill 扩展。**

| 问题类型 | 信息来源 | 回答约束 |
| --- | --- | --- |
| 日常问答 | 当前问题、相关近期对话、一般知识 | 区分用户已说明的事实和一般建议 |
| 历史问答 | 群聊原文、引用关系、后续修正 | 引用证据，缺少证据时说明不足 |
| 混合问答 | 历史证据加一般知识 | 区分已知事实、推导和建议 |

例如“我们之前定了去哪儿，附近有什么好玩的”，应由主 Agent 先获取约定的证据，再结合地点给建议。用户无需为同一问题选择两种能力。

当前尚未接入独立的日常问答 skill 或历史问答 skill，相关基础规则仍在主提示词中。

## Q4：不知道用户意图时，默认上下文怎么选？

**当前实现：先构建小而固定的起始上下文，不依赖模型先准确判断意图。**

| 信息 | 默认规则 |
| --- | --- |
| 系统规则、可用能力、输出 Schema | 从程序模板加载 |
| 当前提问 | 完整保留消息 ID、发送者、发送时间、正文和问题 |
| 身份 | 当前群组、提问人、群成员 ID 与昵称、AI 身份 |
| 时间 | 执行时间、当前提问时间、`Asia/Shanghai` 时区 |
| 直接关联原文 | 按已有 `reply_to_id` 关系补取，优先保留 |
| 近期背景 | 从近到远选择完整消息，最多 12 条、合计 4 KiB |
| 覆盖信息 | 记录选择策略，以及是否省略更早历史 |

当前提问和直接关联原文不占近期背景的 4 KiB，但仍计入完整模型请求预算。4 KiB 是序列化消息的保守字节预算，不是精确的 4096 Token。

默认不附带全部待办、长期记忆或历史摘要。关联原文读取能力不等于前端已经提供回复消息的操作入口。

## Q5：这些信息按什么顺序装入？

**当前实现：当前提问与直接关联原文优先，然后按剩余预算装入近期背景。**

处理顺序：

1. 验证群组、成员和当前消息。
2. 保留完整当前消息，补入直接关联原文并去重。
3. 注入身份、执行时间、时区和覆盖范围。
4. 从近期候选消息向前装入，受数量、背景字节预算和总容量共同约束。
5. 还原原始顺序；时间戳相同也保持消息顺序。
6. 再次验证必需消息、授权范围和完整请求预算。

近期背景中的下一条完整消息放不下时停止向前装入，不截断其正文，也不跳过该条继续拼接更早消息。

这属于近期窗口策略，尚未按语义识别话题边界或判断消息相关性。

## Q6：上下文为什么通过函数注入？怎么扩展？

**当前实现：数据加载与上下文选择之间已有可替换的函数入口。**

```go
type ContextInjector func(context.Context, ContextRequest) (Context, error)
```

`ContextRequest` 提供授权快照、当前消息 ID、问题、关联原文、执行时间和容量。默认实现为 [`InjectDefaultContext`](../../services/api/internal/ai/context/policy.go)，任务执行器装配时可以传入替换或包装函数，见 [`jobs.New`](../../services/api/internal/ai/jobs/worker.go)。

附加任务规则也应采用函数注入契约。迁移前曾提供 `WithMainInstructions(fn)` 字符串指令入口，新目录中的 skill 装配仍待接入；不能把旧构造函数名称当作稳定接口，也不能把附加一段指令等同于已有完整 skill 加载器或工具调用能力。

扩展函数之后仍执行必需消息检查、群组和成员校验、消息截止范围检查，以及最终容量检查。

**后续方向：先确定本次需要的完整指令和能力说明，再分配可选背景预算。** 逐次请求超限直接失败；当前没有根据新加载的规则或工具描述重新压缩、重选背景的通用流程。

## Q7：为什么已经能引用历史，还要历史检索工具？

**当前实现：模型可以引用已经放进上下文的原文，但不能主动搜索未提供的更早消息。**

| 能力 | 当前状态 |
| --- | --- |
| 读取近期群聊历史 | 已实现 |
| 补取直接关联原文 | 已实现 |
| 引用原文消息 ID 并校验 | 已实现 |
| 按问题检索完整群聊历史 | 独立 Memory 检索方法已实现；主 Agent 尚未接入 |
| 自动补充相邻对话、后续修正和相关事项 | 未实现通用检索流程 |

历史检索工具应在未来接入独立 Memory 检索方法，按问题、人员、时间取证。所有取数仍必须遵守授权群组和原提问截止范围；当前检索方法的日期过滤不等于已经接入主 Agent 的原提问 seq 截止范围，接工具时仍需补齐。记忆后台与重启恢复见[历史向量化与增量记忆](历史向量化与增量记忆.md)。

## Q8：超出模型容量时怎么处理？

**当前实现：先缩减可选背景；必需信息或最终请求仍超限时，本地返回错误，不发送该次模型请求。**

完整预算包含系统提示词、附加规则、消息和角色、单独传递的 Schema、协议余量及 2048 输出预留。Schema 同时出现在系统提示和独立参数时，两份都计入估算。

上下文构建、主 Agent 调用前和统一模型适配器均执行容量检查；有效容量取请求与启动配置的较小值。算法是保守 UTF-8 字节估算，尚未使用模型专用 tokenizer。

一次任务若已执行主 Agent，随后发现提取请求超限，只会阻止提取阶段的模型请求；“超限不调用模型”针对每次独立请求，不代表撤销此前已经完成的调用。

实现见 [`llm/budget.go`](../../services/api/internal/llm/budget.go)。

## Q9：怎样防止跨群读取，或者重试时混入后来的消息？

**当前实现：鉴权和消息截止范围由程序控制，不能由模型决定。**

- 数据库保存提问时，同时固定任务的 `context_end_seq`。
- 取数要求群组有效、请求人属于该群，消息 `seq <= context_end_seq`。
- 自定义注入函数返回后，再检查选中消息是否仍属于该群和截止范围。
- 重试使用同一个任务和原始截止范围。
- 主 Agent 委派提取时，继续传递当前请求元数据和直接关联原文，并验证群组与请求人一致。

授权范围和消息序号边界属于服务端约束；Prompt 中的隐私规则作为补充。

## Q10：答案和引用如何校验？

**当前实现：模型输出必须通过结构与来源校验，失败不会作为正常回答保存。**

答案使用 `answered`、`insufficient_evidence`、`conflicting_evidence` 三种状态；`basis` 区分 `general`、`history`、`mixed`。

历史或混合依据的 `answered`、`conflicting_evidence` 必须有来源。所有引用都必须来自本次输入的消息，不允许未知、重复或跨群来源。一般知识可以不引用群聊记录。

来源 ID 合法不等于语义正确。引用是否真正支持结论、是否遗漏后续改口，以及模型是否正确选择 basis，仍需要案例评测与人工核对。

## Q11：工具、skill 和子 Agent 分别解决什么问题？

**设计方向：按执行职责区分，不按名称或代码量区分。**

| 形式 | 职责 | 示例 |
| --- | --- | --- |
| 工具 | 执行明确操作，返回可验证的结果 | 历史检索、待办提取 |
| skill | 提供按需加载的任务规则、步骤和证据要求 | 历史问答规则、日常问答规则 |
| 子 Agent | 在独立上下文中自主判断、规划和调用多个工具 | 后续需要独立多步决策的复杂模块 |

工具可以包含多次模型调用和独立上下文；skill 不必增加一次模型调用。只有模块需要独立决策、持续补证据和调整步骤时，再考虑拆子 Agent。

## Q12：当前有哪些“路由”？为什么没有一张统一能力表？

**当前实现仍是固定分支，尚未建立统一工具目录。**

1. `chat.Service.Send` 判断 @AI 和兼容命令；默认 AI 请求保存为 `auto`。
2. 任务执行层通过统一执行入口选择主 Agent，已有显式 `qa/help/extract` 模式进入主 Agent 的兼容能力路径。
3. 主 Agent 根据受 Schema 约束的 `answer/extract` 决策直接回答或执行提取。

拆包中的 [`runtime`](../../services/api/internal/ai/runtime/runtime.go) 已提供按 Agent ID 分发的注册表。它与主 Agent 内部的工具选择是不同层次：当前自动请求选择 main，main 内仍只有上述固定 action 分支，尚无统一工具注册或通用工具执行框架。

**后续方向：集中声明工具名称、描述、参数、处理函数和权限范围，通过统一执行器分发。** skill 则采用独立的指令加载目录，不把每个 skill 当作一个路由终点。

## Q13：待办提取应保留为子 Agent，还是收敛为工具？

**设计方向：保留已有固定流程，包装为只读的 `extract_todos` 工具；当前无需独立的自主 Agent。**

合理的职责边界是“从指定证据范围提取并核对行动建议”：

| 契约 | 内容 |
| --- | --- |
| 输入 | 当前提取请求、指定范围的授权原文、成员身份、相关已有任务与状态 |
| 处理 | 识别明确承诺，核对负责人和时间，检查完成、取消、修改及可能重复 |
| 输出 | 候选行动、负责人、原时间表达、来源 ID，以及可供程序核验的结果 |
| 外部动作边界 | 不创建任务、不设置提醒、不修改完成状态、不执行行动 |

提取范围由用户请求和主 Agent 明确；有关键歧义时先澄清。后续状态证据用于核对对应行动，不应扩大候选行动的范围。任务创建等写操作由独立工具承接。

**当前代码与目标仍有差距：**

- `ExecuteMain` 仍直接调用既有固定提取 Workflow；拆包将它收敛为主 Agent 内部提取能力，尚无通用 `extract_todos` 工具注册，也没有独立自主子 Agent 的决策循环。
- 群聊路径仍读取截至原提问的完整提取快照，超限会拒绝；更精确的证据范围等待后续检索能力。
- Workflow 支持根据 `input.Tasks` 检查重复，但群聊路径目前始终传入空 Tasks；已有任务状态尚未接通，不能承诺完整去重。

提取实现见 [`workflow.go`](../../services/api/internal/ai/agent/main/workflow.go)、[`acceptance.go`](../../services/api/internal/ai/agent/main/acceptance.go)、[`action_review.go`](../../services/api/internal/ai/agent/main/action_review.go)。

## Q14：主 Agent 当前会收到提取结果并继续组织回复吗？

**当前实现不会再次调用主 Agent。** 主 Agent 选择 `extract` 后执行提取，提取运行结果成为最终运行结果，再由 `ResultFromRun` 转成回复文本。

因此目前是：

```text
主 Agent 决策 → 提取 Workflow → 程序格式化 → 保存回复
```

**目标流程是：**

```text
主 Agent → 调用工具 → 接收结构化工具结果 → 继续判断或组织最终回复
```

这需要增加有步数、总时长和容量限制的工具执行循环。当前还没有通用循环，也没有多工具串联。只有确实需要工具时才进入循环，普通问答继续争取一次调用完成。

## Q15：Worker 与主 Agent 的职责如何划分？

**当前实现：Worker 管理执行生命周期，主 Agent 管理本次请求的回答和能力选择。**

Worker 使用 PostgreSQL `agent_runs` 作为任务队列，在 API 进程内运行两个 goroutine。通过事务锁和 `SKIP LOCKED` 支持不同群并行、同群串行；租约过期后恢复任务，完成时校验 attempt 和租约，阻止旧执行者重复写入。

Worker 还负责执行超时、错误归类、结果落库和 Trace 衔接。它不应随着工具增多而累积新的意图或工具分发分支。

调度实现见 [`ai/jobs/worker.go`](../../services/api/internal/ai/jobs/worker.go)，数据库领取与完成逻辑见 [`chat/job_store.go`](../../services/api/internal/chat/job_store.go)，消息快照适配见 [`chat/context_store.go`](../../services/api/internal/chat/context_store.go)，应用装配见 [`cmd/api/main.go`](../../services/api/cmd/api/main.go)。

## Q16：HTTP、WebSocket 和数据库各负责什么？

**当前实现：HTTP 承接业务请求，WebSocket 通知变化，数据库保存权威状态。**

发送消息、读取历史和重试通过 HTTP。AI 请求先保存为排队任务，再由后台执行，不依赖浏览器保持连接。回复与任务成功状态在同一事务保存，随后通过数据库通知与 WebSocket 提示前端重新拉取。

断线后按消息序号补拉；WebSocket 不承担任务队列或最终状态存储。当前模型调用为非流式，逐字输出属于后续独立扩展。

## Q18：后续按什么顺序扩展？

**设计方向：先明确能力契约，再增加能力数量。**

1. 集中声明当前可用能力，定义统一工具请求、结果与授权范围。
2. 将既有待办提取包装成只读工具，补齐相关任务状态数据。
3. 加入受限工具循环，让结果返回主 Agent，统一组织回复。
4. 接入历史检索，按需补齐原文、相邻对话和后续修正。
5. 按需加载两种问答 skill，并将完整指令纳入上下文预算分配。
6. 隔离已有兼容入口；模块出现独立规划与多步工具协作需求后，再拆子 Agent。

目标结构：

```text
聊天任务执行层
  └─ 主 Agent
      ├─ 指令与 skill 加载
      ├─ 上下文构建与预算管理
      ├─ 统一工具执行
      │   ├─ search_history
      │   └─ extract_todos
      └─ 证据校验与最终回复
```

该结构是扩展目标；不能把图中的工具目录、skill 加载和执行循环视为当前已经实现。

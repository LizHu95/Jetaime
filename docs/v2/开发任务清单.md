## 1. 本周交付与默认选择

主链路：**读取本地聊天历史 → 选择群组和模拟成员 → 提问 → 回答并查看原消息 → 提取待办建议 → 确认 / 修改 / 忽略 → 保存 → 查看本人待办 → 完成 → 重启后恢复**。

已确认：第一周本地可运行；先历史问答与来源引用，再待办提取；User、Group、GroupMember、Message、Task 五类实体；不单独建“消息历史”与 Memory。

本清单建议的实施默认值：

- 沿用仓库 Go 模块和本地 Ollama，以独立本地 HTTP 服务与最简调试页面跑通。
- 固定两个模拟用户、一个主群组，JSON 文件输入和保存；不实现真实登录、邀请或消息实时同步。
- 准备一个额外隔离群组作为测试资料，验证不会混用其他群上下文。
- 按需调用模型：问答和手动提取分开触发；不在本周实现自动介入判断。
- 一次发送当前授权群组的一段短历史，保留消息 ID、发送者、时间和正文；超出容量明确拒绝，不静默截断。
- 待办默认一个负责人，允许时间待定；第一周只完成创建、查看和完成，已有任务的复杂变更 / 取消后续补充。

以上是本轮最简实现的默认值，不代表最终产品形态。本周不做 PostgreSQL、Embedding、增量摘要、长期记忆、多候选决策、群组邀请和视觉重做。

## 2. 最小数据与模型输出

| 对象 | 本周字段与规则 |
| --- | --- |
| User | `id`、`nickname`；固定演示身份 |
| Group | `id`、`name` |
| GroupMember | `groupId`、`userId`；组装上下文前检查成员关系 |
| Message | `id`、`groupId`、`senderId`、`sentAt`、`text`；ID 稳定唯一，发送者属于对应群组 |
| Task | `id`、`groupId`、`title`、`assigneeId`、`dueAt`（可空）、`status`、`sourceMessageIds`、`confirmationKey`；ID 由程序生成 |

源消息有时间与时区；“明天”等相对时间以原消息发送时间解释，而非回放当天。暂时无法可靠确定的时间保留原表达，待确认，不强行生成日期。

问答输出建议为：`status`（answered / insufficient_evidence / conflicting_evidence）、`answer`、`sourceMessageIds`。本周先验证历史事实问答，不以一般知识回答替代历史依据。

待办建议输出建议为：`title`、`assigneeId`（可空）、`dueAt`（可空）、`timeExpression`、`sourceMessageIds`。模型输出是建议；正式 Task 只在用户确认后创建，缺少负责人时必须先选择。

建议暂存在当前提取批次内，由程序分配稳定的建议标识。正式待办保留确认键并与任务一起写入，用于防止重复确认。重新提取时比较已有待办及来源，不把“确认按钮不重复”误认为已经解决所有语义重复问题。

## 3. 开发任务与依赖

所有任务当前状态为“待开始”。工时为初始估算，不含首次下载模型、环境故障与不可预见的模型效果调整。

| 编号 | 任务与交付 | 依赖 | 验收条件 | 估算 |
| --- | --- | --- | --- | --- |
| V2-01 | 定义五类实体、问答结果、待办建议及校验规则 | 无 | 能加载固定用户与群组；消息 ID、成员关系、任务负责人和来源关系可校验；不沿用 V1 的决策 Task 枚举作为待办实体 | 1–2h |
| V2-02 | JSON 聊天资料读取、排序与上下文组装 | V2-01 | 当前成员只读取当前群组；非法 / 重复消息 ID 或发送者报错；消息顺序稳定；短历史完整传入，容量不足明确报错 | 1–2h |
| V2-03 | 适配 V2 模型调用与观测 | V2-01 | 问答 / 提取能分别调用真实 Ollama；可配置模型与超时；保存 Prompt 版本、耗时、错误和模型实际返回的 Token；非法 JSON 不显示成功 | 2–3h |
| V2-04 | 历史问答 Prompt、Schema 与来源校验 | V2-02、V2-03 | 有依据返回答案与原消息；来源 ID 必须属于本次输入；无证据或冲突如实说明；记录原始输出便于人工检查 | 2h |
| V2-05 | 调试页面贯通“提问 → 回答 → 查看来源” | V2-04 | 本地可输入问题、查看来源发送者 / 时间 / 正文；失败保留问题可重试；运行说明可复现 | 1h |
| V2-06 | 待办提取 Prompt、Schema 与建议校验 | V2-02、V2-03、V2-05 | 区分明确行动与讨论意向；“我”对应原消息发送者；来源有效；负责人未知或时间不明确时留待确认；重新提取考虑已确认任务 | 2–3h |
| V2-07 | 确认 / 修改 / 忽略建议，原子保存正式任务 | V2-01、V2-06 | 未确认不写 Task；确认前可修改标题 / 负责人 / 时间；只接受本群成员；重复确认不重复创建；写入失败保留建议，文件不损坏 | 2h |
| V2-08 | 查看本人待办、完成与重启恢复 | V2-07 | 只列出当前模拟用户负责且有群组访问权的任务；完成后持久化；重启保持任务和确认键，失败不虚报完成 | 1h |
| V2-09 | 核心异常回归与真实模型评测 | V2-05、V2-08 | 第 5 节用例有结果与失败记录；协议校验通过和语义效果通过分别记录；V2 运行与数据恢复正常 | 2h |
| V2-10 | 本地运行文档与一次端到端演示 | V2-09 | 从准备资料到重启验证的步骤可复现，说明限制；另一位成员能体验一个真实协同场景 | 1h |

建议总投入约 15–20 小时。优先顺序为 **V2-01 → 02 → 03 → 04 → 05 → 06 → 07 → 08 → 09 → 10**。这是便于学习的顺序，不要求一次铺开全部模块。

## 4. 七天推进节奏

| 时间 | 工作重点 | 当天应看到的结果 |
| --- | --- | --- |
| 第 1 天 | V2-01、V2-02；检查本地模型可用性 | 程序能读取并校验聊天文件，列出正确群组的消息 |
| 第 2 天 | V2-03、V2-04 | 第一次真实模型问答返回结构化答案与来源 |
| 第 3 天 | V2-04 收尾、V2-05 | 调试页面中能提问并查看原消息；无证据问题不编造 |
| 第 4 天 | V2-06 | 明确行动形成待办建议；意向不直接成为任务 |
| 第 5 天 | V2-07 | 修改 / 确认后保存 Task，重复确认不产生重复项 |
| 第 6 天 | V2-08、V2-09 | 本人任务可查看、完成、重启恢复；异常用例有记录 |
| 第 7 天 | V2-09 收尾、V2-10 | 清理关键失败，实际演示并整理运行说明 |

以开始开发后的七天计，不绑定具体日历日期。第 3 天若真实模型问答仍未稳定，先缩小聊天样本和 Prompt，停止增加功能；不通过去掉来源校验或确认步骤赶进度。

## 5. 最小验证集

| 用例 | 预期 |
| --- | --- |
| 已明确预算：两人 200 元以内 | 准确回答，来源包含预算原消息 |
| 历史没有提到具体餐厅 | 明确证据不足，不编造餐厅 |
| 先说预算 200，后明确改成 300 | 解释更新，以较新明确表达为准并引用依据 |
| 历史有无法判断的矛盾 | 标明冲突，不擅自当成共同决定 |
| 模型返回其他群组或不存在的来源 ID | 校验拒绝，不展示为有效回答 |
| “要不要周末去露营？” | 不生成已确认任务，不直接写入 Task |
| 小夏说“我明天负责订票” | 负责人为小夏；相对日期基于该消息时间 |
| “有人记得订票” | 若形成建议，负责人为空，确认前要求选择 |
| 修改建议后确认 / 忽略建议 | 只保存修改后已确认的任务；忽略不创建 |
| 同一建议重复确认，或重启后再次确认 | 最多创建一次；来源一致但标题变化的再提取需提示可能重复 |
| 完成任务后重启 | 完成状态仍存在，本人视图与文件一致 |
| 模型超时 / 输出损坏 / 上下文过大 / 文件写入失败 | 错误清晰，输入保留，无假成功及损坏任务文件 |

结构校验只能证明 ID、字段与权限合法，不能证明模型解释一定正确。历史回答与待办提取仍需人工核对原消息。失败案例记录到评测结果，修改后重跑受影响用例。

测试重点是来源真实性、群组隔离、时间解析、确认幂等和存储失败恢复，不为每个可逆展示操作编写重复测试。使用固定替身测试协议和异常，使用真实模型单独验证语义效果。

## 6. 复用边界与建议代码位置

一期模型适配与决策链路已删除。V2 使用 `internal/ai/llm/` 中的 Eino 组件调用 Ollama 或 OpenAI 兼容接口，实体、上下文、校验、确认与持久化集中在 `internal/assistant/`，不复用收藏或决策 Task。

建议在现有 Go 模块内使用 `cmd/api` 作为本地 HTTP 调试服务，按实现需要组织 V2 业务代码。不创建第二套仓库或完整空分层。具体包名由实现时确定。

虚构聊天 fixture 可以提交；运行生成的任务文件、原始模型响应和真实私人资料放入 Git 忽略的本地目录。使用临时文件加替换保存，并明确第一周只支持单进程写入，不宣称 JSON 文件具备多人并发事务能力。

## 7. 完成判定与下一轮

第一周交付必须同时满足：真实模型能基于短历史回答并引用来源；明确行动能够提取、确认、保存和完成；重启后恢复；核心错误有可观察结果；运行说明可复现。模型效果未达标时如实记录，不用固定假回答替代真实调用验收。

另外记录使用反馈：另一位成员是否愿意再次使用，是否少翻一次聊天或少遗漏一件事，确认待办是否比手动记事更麻烦。技术跑通不等于产品价值已成立。

有余力再做简单本地页面；多人真实聊天、群组邀请、自动介入、候选决策、长期记忆和检索均进入下一轮，按实际使用失败与需求排序。本周不为完整产品范围提前搭建基础设施。

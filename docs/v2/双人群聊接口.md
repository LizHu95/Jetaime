# 双人群聊、实时同步与共享 AI

更新：2026-10-14。普通文字消息、共享 AI 完整回复、阅读进度、实时推送和断线补拉已接入真实 PostgreSQL。复用基线消息、阅读进度和 AI 任务表；Agent 结果元数据由迁移 000003 添加。消息不可编辑或删除。

## 启动与页面

`make dev` 默认开启 Auth、好友群组、聊天 HTTP、WebSocket 和共享 AI worker，需要有效模型配置。共享 AI 使用 local/models.json 的默认 profile，也可用 `-model-profile` 或原有模型参数覆盖；启动参数固定模型，切换需要重启。显式用 `-chat-ai=false` 关闭 AI 时，@AI 提问仍保存，任务显示 ai_unavailable，不生成假回答。共享 AI 随认证模块启动；显式传 `-chat-ai` 必须同时启用 `-auth`，并提供有效模型配置和对应密钥环境变量。

Web 页面 `/page/chat/` 为群列表，`/page/chat/{groupId}/` 为聊天页；登录成功页和好友群组页均提供入口。前端包含文字发送、同一消息 ID 的失败重试、历史分页、未读角标、定位首条未读、@AI 按钮/文字提问、排队/处理中/失败状态、AI 重试及关闭群聊。桌面双栏、手机单栏。

## HTTP 接口

以下接口均验证 Bearer Token，并从会话确定本人；每次查询或写入要求群为 active 且本人是成员。其他人和关闭群返回 `404 group_not_found`，不会泄露群消息。缺失/过期/撤销 Token 返回 `401 unauthorized`。

路径前缀为 `/api/chat/groups/{groupId}`：

| 方法与后缀 | 输入 | 返回 |
| --- | --- | --- |
| GET（无后缀） | 无 | `{id,members,lastSeq,readSeq,unreadCount,assistantName,aiEnabled}` |
| GET /messages | afterSeq（默认 0），或 beforeSeq；limit 默认/最大 100 | `{messages,hasMore}`，消息始终按 seq 升序 |
| POST /messages | `{content,clientMessageId,mentionsAI?}` | 已保存的消息；重复发送相同内容返回原消息 |
| POST /read | `{seq}` | `{readSeq}`，新的本人阅读进度 |
| GET /runs | 无 | 最新 100 个本群 AI 任务及状态 |
| POST /runs/{runId}/retry | 无需请求体，仅原提问人 | 重试原 failed 任务；重复请求不创建新任务 |
| POST /close | 无需请求体，任一成员 | 逻辑关闭群、停用助手、取消 queued/running 任务 |

消息结构：`{id,groupId,seq,senderType,senderId,senderName,content,mentionsAI,clientMessageId,replyToId,createdAt}`。AI 的 senderType 为 assistant、senderId 为 null，replyToId 指向提问，clientMessageId 为 null。AI 任务包含 id、triggerMessageId、requestedBy、contextEndSeq、status、attempt、errorCode、responseMessageId。

文字消息最多 4000 个 Unicode 字符，不允许全空白或空字符；请求体最多 32 KiB，须为 application/json，拒绝未知字段。clientMessageId 是标准 UUID。相同发送人 + clientMessageId 只能对应同一群、内容和 AI 触发状态，复用为不同消息返回 `409 message_conflict`。保存时锁定群行，分配连续 seq，插入消息和可选 AI 任务后一起提交。未成功事务不消耗序号。

## 阅读进度与未读

每位成员只维护一个 last_read_seq。服务端取新旧进度最大值，并限制不超过群内 last_message_seq。未读为 `seq > last_read_seq` 且 sender_user_id 不是本人的消息数量；AI 消息对双方都计入。

客户端只在页面可见、有焦点、消息尾部实际处于聊天可视区域时上报进度。打开列表、后台标签、仅收到实时通知都不会清除未读。初次打开群定位第一条未读；读取进度通知只推送给本人的在线设备，其他成员的已读状态本期不展示。

## 实时协议

`GET /api/chat/events` 升级为 WebSocket，验证同源 Origin。浏览器连接后 5 秒内发送第一帧：`{"type":"authenticate","token":"Bearer 原始 Token"}`；成功返回 `{"type":"ready"}`。Token 不放 URL 或 subprotocol。认证失败以 1008 关闭，临时认证服务错误以 1013 关闭并允许重连。

事件为 `{type,groupId?,actorId?}`，type 包括 message、read、ai、group_closed、resync。事件仅是更新提示，不携带聊天内容或凭据。HTTP 事务内 pg_notify 在提交后生效；每个 API 实例用独立 PostgreSQL LISTEN 连接接收通知，按群成员分发。read 仅分发到阅读人的设备；关闭通知发给双方。慢客户端收到 resync，队列有界。

连接每 15 秒 ping；每 2 秒及每次发送通知前重新校验数据库会话，退出、改密和过期使旧连接关闭。客户端指数退避重连，ready/resync 后重查群列表、阅读进度、任务，并按最后连续收到的 seq 补拉消息。每 15 秒及重新聚焦也与数据库校对，修复通知丢失；重连、重复通知和 HTTP 重试按消息 ID 去重并按 seq 排序。应用关闭时没有系统推送。

## AI 队列与回复

普通消息不触发模型；@AI 按钮设置 mentionsAI，或正文包含独立 @AI 标记后触发。提问与唯一 queued 任务在同一事务保存。两个 worker 可处理不同群，同一群最多一个有效 running 租约，按提问 seq 排队。每次领取增加 attempt_count，并设定模型超时 + 30 秒租约。过期任务恢复后仍使用同一个任务 ID；晚到结果按 attempt_count 和租约进行隔离。

上下文只取本群 `seq <= context_end_seq` 的消息，不含未来对话、其他群或单独私有资料。起始上下文保留当前问题、直接引用和最多 12 条/4 KiB 背景。main 按工具目录选择 `answer_question` 或 `set_reminder`；QA 根据模式补充近期原文、历史混合检索与来源回查。`extract_todos` 已移除默认注册，行动事项总结由 QA 以文字回答。所有请求计入系统规则、Schema、元数据和输出预留；必需信息超限返回 context_too_large。

结果中的 historyScope 说明选取策略、省略范围及是否检索过历史。来源只能来自本次实际输入的原文。工具输出结构与来源校验失败时，不保存为成功回答。完整能力与预算边界见[主 Agent 设计问答](主Agent设计问答.md)。

所有推理请求均执行本地容量保险：QA、提取、接受核对、行动核对在调用前检查，统一模型适配器在任何模型 HTTP 请求之前再次检查。预算包含全部消息与角色、单独传递的 Schema（即使提示词中已有一份）、每条消息的协议开销、512 余量及请求的输出预留；容量取启动配置与请求 num_ctx 的较小值。容量或输出预留缺失、或预算超限时返回可识别的容量错误，群聊归类为 context_too_large，不调用模型，也不自动重试。此检查仍为保守 UTF-8 字节估算，并非模型专用 tokenizer 的精确计数。

完整回答保存为一条 assistant 消息，分配同一群消息序号，关联提问，更新任务 succeeded，并在提交后向双方通知。同一任务最多保存一个回答；AI 排队/处理中/失败状态不算未读。用户离线不取消任务；关闭群时取消队列及运行状态，晚到模型输出不能落库。原提问人可重试失败任务，提问消息和任务不重复创建。

## 一次性提醒（2026-10-20）

提醒是独立业务领域。`internal/reminder` 提供 Service、Store、HTTP Handler 和 Worker，不导入 AI/LLM 包。Service 提供 Create、Update、Draft、CancelDraft、List 和 Cancel；校验日期/时刻、权限和版本，返回结构化 Result。Store 保存数据、操作结果和事务；Worker 每秒扫描到期的 pending 提醒，写入群消息并将状态改为 sent，沿用实时通知与 Web Push 向群成员推送，不调用模型。

`internal/ai/tools/reminder` 仅适配 LLM：定义 set_reminder 的参数、读取后端上下文中的草稿、转换调用参数、调用领域 Service 并将业务结果转换为追问/成功回复。tool 与 HTTP Handler 调用同一个 Service，无需绕经本机 HTTP。AI 任务租约、attempt 和触发消息校验由 chat 层注入事务 Guard，提醒领域不依赖 agent_runs 或 tools.Scope。终结工具的结构化业务结果也写入 AI 执行步骤，不能根据模型口头回复认定创建成功。工具输入输出由 Go 类型推导 Schema，统一执行器校验；工具返回业务结果，主 Agent 组装执行记录，详见[工具契约与开发](工具契约与开发.md)。

首次在群里 @AI 请求设置提醒。缺日期或时刻时创建 status=draft 的记录；后续补充更新同一个 reminderId。示例：「提醒我吃饭」→「你想哪天、几点提醒？」→「明天」→「明天几点？」→「中午12点」→ status=pending，确认创建。草稿按群和请求者隔离，24小时内续答无需重复 @AI。set_reminder 的 sourceMessageIds 指向当前请求和同一用户的相关原始安排消息；历史时间只在模型明确引用该消息时才通过校验，不从无关背景或其他成员消息借用时刻。历史相对时间按原消息 sentAt 和 Asia/Shanghai 解析，已有明确时刻不重复追问。回复来源包含请求与原始安排。适配器不接受模型凭空补时刻；领域负责完整时间及未来时间校验；HTTP 调用可直接传确定的业务时间，无需聊天文本。时间按 Asia/Shanghai 解析和展示。周期或单次请求包含多条提醒暂不支持。

数据库最终保留两张表：

- reminders：统一保存 draft / pending / sent / cancelled。日期和时刻可分别保存，draft 的 due_at 为 NULL，时间完整才变为 pending。每个用户在每个群最多一个 draft；补全期间 ID 不变。version 防止旧请求覆盖更新，sent_at 与 delivery_message_id 记录实际发送。
- reminder_operations：以 operation_id 去重，保存群、请求者、可选来源消息和结构化 result。创建、更新和操作结果在同一事务提交；旧请求重放返回原结果，不回退提醒状态。HTTP 的 operationId 独立于 AI 任务；tool 使用触发消息 ID，并附带租约 Guard。

HTTP 接口均要求有效登录和本群成员权限，修改仅限创建者：

- POST /api/chat/groups/{group}/reminders：创建提醒或草稿。请求含 operationId（UUID）、title、可选 date（YYYY-MM-DD）、time（HH:mm）。
- PATCH /api/chat/groups/{group}/reminders/{reminder}：补全或修改，含新的 operationId、当前 version，按需传 title/date/time；status 可设 pending 或 cancelled。完整草稿自动进入 pending；sent 只能由 Worker 设置，已发送/已取消记录不能重新激活。
- GET /api/chat/groups/{group}/reminders：配置列表，返回本群正式提醒及取消记录；草稿通过领域 Draft 方法提供给对话上下文。
- POST /api/chat/groups/{group}/reminders/{reminder}/cancel：兼容配置页面的幂等取消接口。

创建/更新响应包含 status（needs_clarification / created / updated / cancelled）、reminderId、reminder、missingFields（date/time），过去时间另有 reason=time_in_past。版本不匹配返回 HTTP 409；缺权限/目标不存在返回 404；非法状态返回 400。重复调用同一 operationId 返回此前结果。

群聊右上角为「配置」，展示待提醒、已提醒、已取消记录；关闭群聊按钮暂时隐藏，关闭 API 保留。取消未补全草稿后，列表显示「时间未补全」。

部署前应用全部迁移，包括 000009_reminders.up.sql 和 000010_reminder_domain.up.sql。后者将已有草稿迁入 reminders，保留正式提醒和旧操作结果，再移除 reminder_drafts。发送群消息和更新 sent 状态在同一事务内完成；重启后补发未发送的到期事项，关闭群后不再发送。Web Push 的设备投递与重试仍由推送领域负责。

验证覆盖独立业务 HTTP API（不调用 AI）、同一草稿逐步补全、版本/状态校验、操作重放、权限隔离、旧 AI worker 与恢复重试、多 worker 单次投递、旧表数据升级，以及桌面/手机对话和配置列表。模型决策测试使用受控响应，未进行真实模型质量评测。

### 失败诊断与 Phoenix

`GET /api/chat/groups/{group}/runs` 返回每个任务的 `traceId: string | null` 和 `attempt`。`traceId` 是实际执行链的 32 位十六进制 OpenTelemetry Trace ID，可在 Phoenix 按 Trace ID 定位整条链；业务任务 `id` 对应 span 属性 `chat.run_id`。失败原因弹窗支持复制 Trace ID、任务 ID、群 ID、触发消息 ID、错误码和执行次数，不复制聊天正文或模型响应。

Trace ID 在任务完成事务中保存；AI 未启用等直接入队失败保存入队阶段的 Trace ID。重试与重新认领时清空，随后写入本次执行的 ID。未记录或未采样的任务返回 `null`，旧记录不推测补填；采集传输失败或数据过期时 Phoenix 可能查不到对应链。新增迁移 `000011_agent_run_trace_id.up.sql`，部署时执行 `bash start.sh restart` 自动应用。

正式群聊的 AI Worker 在初始上下文阶段固定执行混合检索，查询沿用原问题，截止范围使用后端 `context_end_seq`；QA 参数只保留 question，无上下文模式枚举或选择分支。检索完成后主 Agent 可通过 respond 直接回答，同一问题的 QA 调用复用检索结果。

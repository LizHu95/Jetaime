# 今天干嘛 技术选型方案 V0.1 草案

日期：2026-10-08。依据：产品方案 PRD V0.3。适用范围：两个成员共享生活空间的 MVP。

建议采用 Taro + React + TypeScript、Go + Gin、PostgreSQL、私有对象存储和直接调用模型 API 的组合。服务端先筛选收藏，再让模型组合方案，最后校验并返回。先交付双人共享和真实数据，再接入 AI 整理、推荐与反馈。

PRD 中的技术栈是建议，本方案将其作为选型起点；以下推荐尚未代表已完成实现或性能验证。默认按微信小程序为正式入口、H5 用于预览规划，交付优先级等待用户反馈后调整。当前仓库为空，PRD 提及的 HTML 原型未随本次文件提供。

## 1 交付路线选择

| 路线 | 组合 | 优点 | 代价与适用条件 | 建议 |
| --- | --- | --- | --- | --- |
| A 小程序与 H5 共用前端 | Taro + React + TypeScript，Go API | 适合 PRD 的正式小程序方向；复用页面与业务逻辑 | 登录、上传、存储等仍需端适配；两个端都要验证 | 默认推荐 |
| B 先交付 H5 | React + TypeScript + Vite，Go API | 浏览器开发与交互验证直接 | 小程序后续需要另做部分界面与平台适配；业务类型和 API 可复用 | 适合小程序暂不确定的情况 |
| C 只交付小程序 | 微信原生小程序 + TypeScript，Go API | 平台能力直接使用 | H5 预览需要另一套界面 | 适合明确只使用微信的情况 |

Taro 官方支持 React 和多端输出，但跨端行为仍可能需要不同实现。因此路线 A 是代码复用策略，并不承诺所有端零适配。[Taro 介绍](https://docs.taro.zone/docs/)、[多端开发](https://docs.taro.zone/docs/guide/)

若已有 Vue 开发经验，可将 A 替换为 Vue 跨端方案；目前没有现有代码或团队经验依据支持为此改变 PRD 的 React 起点。V1 暂不引入 SSR，核心价值在登录后的移动端操作闭环。

## 2 模块选型与取舍

| 模块 | 建议选择 | 可选方案 | 选择依据与切换条件 |
| --- | --- | --- | --- |
| 前端 | Taro + React + TypeScript | React + Vite、原生小程序 | 由第一版交付入口决定 |
| 后端 | Go + Gin 单体 | Go 标准库 HTTP | 延续 PRD；按业务模块组织代码，减少框架选择成本 |
| 数据库 | PostgreSQL | SQLite、MySQL | 共享关系、事务、结构化扩展字段适合关系库；本地与线上保持同一引擎 |
| 数据访问 | pgx + sqlc | GORM | SQL 中显式表达空间隔离、筛选和锁；接受 SQL 编写与代码生成流程 |
| 数据迁移 | 版本化 SQL 迁移 | ORM 自动迁移 | 建表与修改可审阅，部署执行明确；迁移工具在骨架阶段锁定 |
| API 协议 | REST JSON + OpenAPI | GraphQL | CRUD 和两个 AI 工作流足够；以合同生成 TS 类型，避免双端字段漂移 |
| 前端状态 | React 局部状态，封装 API hooks | 全局状态库 | 表单与推荐会话先保持局部；跨页复杂状态出现后再引入 |
| 图片 | 私有对象存储，服务端代理上传起步 | 客户端签名直传、本地文件 | 两人低流量先简化上传；本地目录仅用于开发 |
| 搜索 | PostgreSQL 分类过滤、标题与标签匹配 | pg_trgm、向量检索 | 小规模库先确保中文子串和精确标签可用；按评测结果升级 |
| AI | 单供应商 API + 薄适配层 | 两个模型分工、自部署模型 | 先验证一个供应商能否完成两个工作流；不做复杂模型路由 |
| 会话 | 服务端随机会话，PostgreSQL 保存会话摘要 | JWT + 撤销机制 | 两人规模下易撤销、易排查；不因会话额外引入 Redis |
| 部署 | 单机 Docker Compose + HTTPS 反向代理 | 托管数据库、托管容器 | 控制起步复杂度；若不愿维护数据库，改为托管 PostgreSQL |

sqlc 根据 SQL 生成 Go 数据访问代码，支持 pgx/v5；数据库迁移需要独立执行。这里推荐它，是为了让跨空间查询与事务条件保持显式。[sqlc 生成文档](https://docs.sqlc.dev/en/latest/howto/generate.html)

GORM 提供关联、事务和 CRUD 能力；若开发者更熟悉 ORM，也可采用 GORM，但查询仍须显式包含空间条件，生产建表仍使用版本化迁移。[GORM 官方文档](https://gorm.io/docs/)

pg_trgm 可支持相似匹配及部分 LIKE 查询的索引加速；中文短词效果需使用真实收藏验证，不能将其视为中文语义搜索。[PostgreSQL pg_trgm 文档](https://www.postgresql.org/docs/current/pgtrgm.html)

## 3 服务端架构

请求流：小程序或 H5 → HTTPS API → 鉴权与空间校验 → 业务服务 → PostgreSQL、对象存储或模型 API。

单个 Go 服务包含六个业务模块：auth、space、ideas、assets、decisions、plans。HTTP handler 负责协议转换，service 负责规则和事务，数据库查询及模型调用独立封装。API 密钥与微信凭证只保留在服务端。

推荐目录如下，骨架阶段再生成实际文件：

```text
apps/client/             Taro 页面与平台适配
services/api/cmd/        服务入口
services/api/internal/   按业务模块组织
services/api/db/         SQL 查询和迁移
contracts/openapi.yaml  前后端接口合同
deploy/                 Compose 与代理配置
docs/                   产品与技术文档
```

V1 不引入微服务、MQ、Redis 或向量数据库。普通 CRUD 与 AI 请求分别设置超时和并发限制；模型阻塞不会持有数据库事务或耗尽普通请求资源。需要后台任务时先评估 PostgreSQL 持久化任务表，再判断是否需要独立队列。

## 4 模型接入选择

| 方案 | 优点 | 代价 | 建议 |
| --- | --- | --- | --- |
| 一个多模态模型承担整理与决策 | 接入与排查简单，共用供应商能力 | 未必在两项任务上都最优 | 作为起点 |
| 视觉模型整理，文本模型决策 | 可分别优化成本和效果 | 多一套配置与评测，错误定位更复杂 | 实测收益明确后切换 |
| 自部署模型 | 可自行控制运行环境 | 运维、硬件和模型服务成本 | 暂不选 |

供应商和模型 ID 暂不锁定。若主要在中国大陆使用，可优先用可访问的托管服务开展验证，例如阿里云百炼；最终选择取决于部署地域、账号可用性、图片识别质量、结构化能力、延迟与实测成本。接口形式兼容不代表模型能力一致。

优先选择支持 JSON Schema 的模型；仅提供 JSON Object 的模型还需额外保证结构。百炼文档区分这两种模式，具体模型与运行模式的支持须在接入时核对。即使结构符合 Schema，也必须继续验证事实引用与业务约束。[百炼结构化输出](https://help.aliyun.com/zh/model-studio/qwen-structured-output)

模型适配层只暴露 `ExtractIdea` 和 `Recommend` 两个业务操作，配置供应商、模型、超时和输出上限。首版只实现一个供应商，不提前建设通用 AI 平台。

### 收藏整理

1. 校验图片类型、大小、内容归属并处理图片，文字和链接限制长度。
2. 用户明确触发 AI 整理后，提交必要输入；链接只作为原始素材，不自动抓取正文。
3. 返回待确认草稿，区分原文提取、模型推断和未知字段。地址、价格、营业时间等缺少证据时留空。
4. 用户确认后才写入 IdeaItem；失败保留原始输入并允许手工保存。

### 决策推荐

1. 验证场景、模式和显式约束；自然语言中的禁忌或预算提取后应让用户可见，发现歧义时不静默猜测。
2. 只检索当前空间的收藏，按分类、明确禁忌与适用条件过滤。
3. 使用标签、偏好、近期反馈和本轮排除项做简单排序；候选数量设置可配置上限，不发送完整收藏库。
4. 模型生成主方案与最多两个备选；只负责组合、解释和建议。
5. 校验结构、候选 ID、来源、模式、禁忌及预算等规则，再返回完整结果。

价格或耗时未知时，服务端无法证明方案满足硬约束。硬上限场景应排除缺少必要数据的候选，或返回“信息不足，需确认”，不能把未知当作零。费用统一使用人民币分；菜单耗时考虑并行制作，活动时长包含可识别的间隔；无法确认的交通耗时加入 unknowns。

显式饮食禁忌必须作用于主方案和全部备选；成分信息不足时，不声称适合该禁忌。模型补充的菜品也按相同规则校验。收藏不足时允许方向建议，但不生成未经验证的具体商户事实。

上传文本、图片 OCR 与链接内容都是数据，不能覆盖系统规则。模型无数据库写权限，也不直接访问任意外链。

V1 先使用同步请求并一次返回完整 JSON；在超时预算内最多进行一次输出修复，失败返回明确错误。客户端取消时尝试传播取消信号，但不承诺供应商立即停止计费。若实测耗时超过端侧可靠等待范围，再升级为持久化任务和轮询。

## 5 数据设计边界

保留 PRD 的 User、Space、SpaceMember、IdeaItem、UserPreference、Decision、Plan、Feedback。补充 Session、Asset、AIRequest 和幂等请求记录，用于会话、图片归属、请求排障和防止重复保存。

| 对象或规则 | 建议实现 |
| --- | --- |
| IdeaItem | 分类、标题、描述、标签、来源、创建人和版本号作为明确字段；专属属性放 JSONB |
| 预算与耗时 | 单独列出已知值或区间及证据性质；空值保持未知；估计值与用户确认值分开 |
| Dish 关系 | 可关联同空间的菜谱或餐厅；校验关联目标类别 |
| Decision | 生成结果暂存，用于采纳和重试；不直接展示为历史记录 |
| Plan | 用户采纳或保存待用时创建；复制结果快照，保留操作者和来源关联 |
| Feedback | 建议每个成员对同一 Plan 保留一条可修改评价，唯一键为 plan_id 与 user_id |
| Asset | 存对象 key、空间、上传人和处理状态；不存永久公开地址 |
| 并发编辑 | 乐观版本号，版本冲突返回 409，避免另一人的修改被静默覆盖 |

每张空间业务表均有 space_id；查询和关联均验证归属。成员上限 2 通过空间行锁与事务控制，避免并发加入超过两人。邀请采用一次性、有期限的随机令牌，服务端保存摘要。仅有空间 ID 无法加入空间。

PRD 要求“只保存主动采纳或待用方案”，同时概念模型包含 Decision。建议解释为：未保存生成结果仅短期暂存，不进入用户记录。建议初始保留 24 小时，之后清理；Plan 快照独立保留。AIRequest 日志仅保存必要元数据，避免记录完整图片、偏好和提示词。该保留策略属于新增建议，需在数据合同阶段确定。

删除收藏后，历史 Plan 保留快照。尚未采纳的 Decision 在保存时重新检查来源归属与删除状态，来源失效则提示重新生成。历史快照不依赖仍然存在的收藏外键才能展示。

## 6 接口和一致性

建议接口分组：auth、space、ideas、assets、ai、decisions、plans。业务接口以 `/api/v1` 开头，错误统一返回 code、message、request_id。列表采用有上限的分页，更新携带版本号。

| 操作 | 建议接口 | 核心规则 |
| --- | --- | --- |
| 微信登录 | POST /auth/wechat | 服务端换取身份并签发自己的会话 |
| 邀请加入 | POST /space/invites，POST /space/join | 邀请有限期，一次性，成员上限事务保护 |
| 收藏操作 | GET/POST /ideas，GET/PATCH/DELETE /ideas/{id} | 归属校验与编辑版本检查 |
| 图片上传 | POST /assets | 服务端校验，返回资产 ID |
| AI 草稿 | POST /ai/idea-drafts | 不自动保存收藏 |
| 推荐 | POST /decisions | 生成暂存结果，返回 decision_id |
| 采纳或待用 | POST /plans | 指定 decision_id、方案选项和 planned 或 saved |
| 执行状态 | PATCH /plans/{id} | 验证状态转换与版本 |
| 完成反馈 | PUT /plans/{id}/feedback | 仅 completed 可反馈，校验评价成员归属 |

“换一组”由服务端根据本轮推荐会话维护已看 ID 和方案摘要；排除项不能由客户端作为可信候选来源。素材用完时说明原因，避免硬排除造成完全无结果，也不许为了换一组放宽禁忌。

保存类操作携带 Idempotency-Key，唯一范围包括用户、空间与操作。服务端保存请求摘要及结果；同键同内容返回原结果，同键不同内容报冲突，记录写入与业务变更处于同一事务。建议同一 Decision 选项只对应一个 Plan；从 saved 改为 planned 更新原记录。

建议状态转换：saved → planned/cancelled，planned → completed/cancelled，cancelled → saved/planned。completed 首版不回退。状态变化和操作者记录一起提交。

## 7 登录与图片策略

小程序采用微信登录换服务端会话。H5 开发预览可模拟身份，但服务端仅允许开发配置启用；真实 H5 双人使用需要独立登录方案，不能沿用模拟登录。若用户选择 H5 正式交付，先补充受控账号登录合同。

图片保存在私有 bucket。读取前由 API 验证空间归属，再签发短时访问链接；向模型提供可访问的短时资源或供应商支持的图片数据形式。不得把客户端传入的对象 key 当作授权依据。

上传校验实际图片内容而非只看扩展名，限制解码尺寸和数量，纠正方向并移除 EXIF。截图中的小字可能需要较高分辨率，压缩规格用真实截图评测后确定。未关联收藏的临时资产定期清理。

## 8 部署与验收

开发环境采用 Go API + PostgreSQL + 本地文件存储。线上建议 HTTPS 代理 + Go 容器 + PostgreSQL + 对象存储，数据库与图片不公开服务端口。数据库使用持久化卷，定期将备份保存到主机之外并演练恢复；单机方案接受主机故障时的停机风险。

发布前核对当前微信平台的账号、登录、HTTPS 域名、上传与下载域名要求，以及实际使用供应商的图片处理说明。具体发布条件需以账号后台和微信官方规则为准，不在选型阶段假定全部已具备。

记录 request_id、模型与提示词版本、耗时、错误类型、可用的 token 用量。普通日志不包含会话令牌和完整用户素材；限流和 AI 并发限制先放单实例服务，需多实例时再改为共享实现。

优先验证以下高影响行为：跨空间访问被拒绝、邀请并发不超员、重复点击不重复保存、删除收藏不破坏历史快照、未知价格不通过预算校验、禁忌冲突被拦截、AI 失败仍能手工保存。

AI 评测使用真实约 20 条收藏，覆盖三个吃饭模式、玩什么、空库、偏好冲突、未知信息、虚假引用和图片内指令。将固定输出校验测试与真实模型评测分开；普通 CI 不依赖付费模型随机输出。H5 可跑浏览器 E2E，小程序还需开发者工具和真机验证。

成本由服务器、数据库与备份、图片存储与流量、模型调用组成。模型成本按实际输入输出 token 和图片计费规则计算，同时计入重试；在供应商、地域及使用量未确定前，不给固定月费结论。

## 9 实施顺序与未决项

1. 确定交付路线，形成 OpenAPI、数据字段和状态规则，锁定工具版本。
2. 建立客户端、Go、数据库迁移及本地运行骨架。
3. 完成登录、双人空间、邀请、收藏与私有图片，包含权限与异常路径。
4. 实现 AI 草稿及手工保存降级，使用真实截图评测。
5. 实现候选筛选、吃饭与活动推荐、结果校验和换一组。
6. 实现采纳、待用、完成反馈、历史快照、备份恢复与核心验收。

当前建议：采用路线 A 和 pgx + sqlc，模型先走单供应商。仍需确定首发入口、现有微信账号与部署地域、可用模型账号及预算，以及未采纳结果的保留时间。前端路线影响骨架，模型型号可在真实评测后确定。

# Jetaime Constitution

## Core Principles

### I. 以明确需求和现行事实驱动变更

- 功能变更必须说明用户目标、范围、可观察行为和验收条件；复杂变更必须先形成规格、
  技术方案和可执行任务，再进入实现。Spec Kit 产物用于记录本次变更，不要求补写全部历史规格。
- `docs/v2/` 承载当前产品方向；V1、已退役调试台与评测文档、历史截图和原型
  不得被直接当作当前已实现能力或最终验收标准。
- 必须区分已实现、计划中、未验证和历史行为。描述当前状态必须核对代码及可复现检查；
  若实现偏离已确认需求，必须明确记录差异，不得用实现反向抹去需求。
- 同一行为只维护一份现行契约，其余文档引用该契约。发现冲突必须指出依据；
  判断现状时优先核对当前实现、相关测试和适用目录内的开发约定。

理由：项目已多次演进，必须避免从旧设计重新引入退役能力或制造第二份事实来源。

### II. 领域拥有业务，适配层复用能力

- 后端按业务领域或明确基础设施职责组织。领域拥有业务类型、Service、授权规则、
  事务、持久化和业务 Worker；HTTP、AI 工具及其他入口必须复用对应领域 Service。
- Handler 负责请求解析、响应和领域错误映射，业务入口必须经过 Service。
  AI 工具负责模型协议、参数与上下文适配、输出校验，不得直接执行业务 SQL、
  复制业务状态机或让业务域反向依赖 `ai/tools` 和具体 Agent。
- HTTP 方法和路径必须在 `services/api/internal/httpapi/router.go` 集中注册，
  直接绑定具名 Handler 方法并显式包装鉴权；不得恢复 `Endpoints()` 转接表。
  `httpapi` 不依赖具体业务包，`app` 负责跨域装配和后台生命周期。
- 聊天原文由 `chat.Service` 提供，`chat/history` 承载读取契约；
  AI 提取、记忆、向量与索引归入 `ai/memory`，模型适配归入 `ai/llm`。
- 前端按业务域扩展 `apps/web/src/features/`，复用公共 UI、HTTP 和数据查询基础设施。
  新抽象必须解决明确的复用或隔离问题，不得仅为目录层级添加转接模块。

### III. 服务端授权与 AI 证据边界不可绕过

- 用户身份必须由服务端认证结果确定，不信任请求体中的身份；前端路由守卫不得替代
  后端鉴权。HTTP、WebSocket、AI 工具和后台执行必须保留各自入口的授权校验。
- 访问群聊、记忆、来源与业务操作时必须校验群成员资格和群状态。
  群组、操作者及原提问截止序号必须由服务端提供，模型不得覆盖这些授权边界。
- 历史检索和原文回查必须遵守原提问的消息截止范围；来源引用只允许使用本次实际
  提供给模型并通过校验的原文。记忆摘要不得冒充原始证据。
- 每次模型调用前，执行 Agent 必须检查包含提示词、上下文和工具 Schema 的完整请求预算，
  并保留输出预算；不得只检查聊天正文大小。
- Skill、提示词和模型输出不得扩大工具或写操作权限。写操作必须通过领域 Service，
  AI 执行相关写入还必须校验服务端执行身份、有效 attempt 和租约。
- 面向客户端的业务结果不得包含原始模型响应、内部推理步骤或凭据。

### IV. 数据一致性与可恢复执行

- 必须维持消息与 AI 入队、AI 回复与完成状态的事务一致性。
  群关闭、任务取消和重试不得让过期 Worker 继续提交业务结果。
- 后台处理必须保留持久游标、检查点、租约和重试语义；重复执行不得重复产生
  已完成的业务效果。修改相关流程必须验证中断恢复、重复执行和租约过期行为。
- 数据库是持久业务状态的依据；WebSocket 和 Web Push 用于通知，
  断线或通知丢失后必须能够通过数据库补拉恢复并去重。
- 数据库结构变更必须通过版本化迁移，保留现有事务、并发锁和校验和保护；
  不得为绕过不兼容而修改已应用迁移、清空游标或删除历史数据。
- 记忆 pipeline、向量模型版本或维度变化必须设计兼容性检查、回填和切换方案，
  不得混用不兼容索引。涉及数据转换的变更必须说明失败恢复与验证方式。

### V. 以可复现验证和诊断证据交付

- 验证必须对应实际改变的行为与风险，优先覆盖权限、事务、恢复和用户流程。
  不得把受控模型响应或模拟接口测试表述为真实模型质量或真实服务联调结果。
- 后端及启动脚本变更必须通过适用的 `make check` 检查；前端行为变更必须运行
  适用单元测试、浏览器流程和构建，完整入口为 `make web-check`。
  数据库行为变更必须使用隔离测试库或 schema 运行相关真实数据库测试。
- 无法运行的检查必须记录原因、未验证范围和剩余风险，不得宣称全部通过。
  并发、重试或租约变更必须包含相应并发验证，必要时运行 Go race 检查。
- AI 链路必须保留执行身份、版本、状态、稳定错误原因及 Trace 关联。
  提示词或 Skill 策略变化必须更新其现有版本标识，确保结果可追溯。
- Trace 和日志的正文采集必须遵守配置开关及截断限制；不得记录密钥、完整向量
  或含认证信息的供应商错误正文。关闭正文采集时仍保留必要诊断元数据。

## 技术与数据约束

- 现有主栈为 Go 标准库 HTTP、PostgreSQL/pgx 与 React/TypeScript/Vite。
  依赖和工具版本以 `.go-version`、`go.mod`、npm lockfile 和 Makefile 为准；
  引入新框架或依赖必须说明现有能力不足之处及维护成本。
- 页面采用 `/page/`，业务接口采用 `/api/` 并按领域组织。
  `GET /test/healthz` 是已存在的例外，其固定响应不代表数据库或模型已就绪。
  不得为内部进程协作预先增加无实际调用方的 HTTP 接口。
- SQL 已接入 sqlc 的部分必须修改 SQL 源文件后重新生成，禁止手改生成代码；
  修改对应 schema 时必须同步 sqlc 配置，并通过 `make sqlc-check`。
- `deploy/` 只保存部署定义与无密钥模板；`local/` 保存实际配置、凭据、私有输入
  和持续状态；`outputs/` 保存构建及检查产物。后两者不得提交或公开，
  浏览器可见的 `VITE_*` 配置不得包含密钥。
- 历史快照和冻结证据不得因重构或目录整理而改写。删除唯一历史证据前必须成套归档。
- 服务启动和模型配置必须沿用现有统一入口；不得重新引入已移除的认证开关、
  无数据库启动假设或已退役评测依赖。

## 开发流程与质量门禁

1. 开始前核对适用开发约定、当前代码及现行文档，说明本次范围与验收依据。
   复杂需求使用 `spec.md → plan.md → tasks.md`，并引用已有领域和接口文档。
2. 方案阶段检查上述五项原则，明确授权边界、数据变更、失败恢复与验证路径。
   涉及接口兼容变化时必须列出调用方和迁移方式；不得在无说明的重构中改变 URL、
   请求响应字段或权限语义。
3. 实现保持变更范围可审阅；移动包或调整契约时同步 import、测试、脚本及现行文档。
   只对改变的风险补充有意义的验证，不强制为纯文字或低影响可逆改动新增应用测试。
4. 交付说明必须列出最终行为、实际运行的验证、未验证限制及必要的部署或迁移顺序。
   当前 CI 的 `make check` 不包含 Web 和真实数据库全套检查，不得据此声称这些检查已通过。
5. 评审必须核对 constitution 合规性和规格验收条件；发现偏离时，先修正变更，
   或在方案中记录范围、理由、风险和退出条件，并由项目维护者明确接受后再合并。

## Governance

本 constitution 是本项目 Spec Kit 规格、方案、任务与评审的共同治理基线。
目录内开发约定可以细化规则，但不得静默削弱上述授权、数据一致性和隐私边界。
当前实现用于识别事实和历史差异，不自动构成违反原则的豁免。

修订必须说明触发原因、原则变化、对现有实现和开发流程的影响，以及必要的迁移措施，
由项目维护者在代码评审或明确指示中确认。临时例外必须记录适用范围和退出条件，
不得通过修改模板或提示词隐式变更治理规则。

采用语义化版本：不兼容的原则删除或重新定义提升 MAJOR；新增原则或实质扩展提升 MINOR；
不改变要求的澄清与文字修正提升 PATCH。首次正式建立为 1.0.0，
批准与最后修订日期均为 2026-10-30。每次修订必须同步版本、日期和影响说明。

关联事实来源为 `README.md`、`services/api/internal/AGENTS.md`、`docs/目录约定.md`、
`apps/web/README.md`、现行接口与记忆设计文档，以及代码和 Makefile。
发现旧说明与当前行为冲突时必须记录，修订相关文件另行限定范围；
本次 constitution 建立不自动修改其他文档或模板。
